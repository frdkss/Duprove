# Независимость интерфейса, локальной логики, ядра и сервера

Основание: требование пользователя от 2026-10-13 и просмотренные файлы этапа 1:
`electron/bridge.ts`, `electron/preload.ts`, `electron/services/analyzer-service.ts`,
`docs/architecture.md`, `contracts/README.md`.

Это обязательные правила дальнейшей разработки. Они не означают, что все перечисленные
API и проверки уже реализованы. Сейчас публичный API интерфейса содержит только
`listDrives()`, а серверный HTTP endpoint ещё не реализован.

## Главное требование

Интерфейс можно полностью переделать: заменить компоненты, структуру страниц,
диаграммы, стили и способ навигации — без изменения алгоритмов анализатора,
локального индекса и серверного контракта статистики. При сохранении API такая
переработка не требует пересборки C++-ядра или обновления Python-сервера.

Независимость обеспечивается границами ответственности и контрактами, а не только
разными папками. Общая поставка в одном установщике допустима; прямые зависимости
ядра от визуальных компонентов недопустимы. Это требование совместимости,
а не обещание отсутствия любых ошибок после изменения кода.

## Четыре независимые части

| Часть | Чем владеет | Чего в ней быть не должно |
| --- | --- | --- |
| React UI (`src/`) | Вёрстка, стили, локальное состояние отображения, выбор пользователя, подписи и подсказки | Обход дисков, сравнение файлов, доступ к SQLite, запуск процессов, отправка статистики напрямую |
| Локальная логика приложения | Задания, состояние выполнения, настройки, согласие, очередь отправки, вызовы анализатора | Зависимость от TSX/CSS, конкретного окна, способа рисования диаграммы или существования React-компонента |
| C++-ядро (`duprove-core`) | Обход, идентичность файлов, сравнение, индекс, агрегаты и формирование разрешённого отчёта | React, Electron, браузер, сервер, HTTP, тексты окон и знание о визуальном расположении кнопок |
| Python backend (`backend/`) | Приём, проверка, хранение и обработка обезличенной статистики | Управление локальными дисками, рабочие пути и хеши пользователя, зависимости от UI и C++-библиотеки |

Electron main/preload — адаптер настольной среды. Он связывает UI с локальной
логикой, управляет окнами, треем, уведомлениями и автозапуском. Бизнес-решения
не размещаются в обработчиках React и по возможности не зависят от Electron API:
работа с ОС, процессами и сетью предоставляется через отдельные адаптеры.

## Направление взаимодействия

1. UI вызывает разрешённый метод локального API через preload.
2. Локальная логика проверяет запрос, изменяет состояние задания и обращается
   к адаптеру анализатора.
3. Адаптер переводит запрос в CLI/NDJSON, запускает C++-процесс и проверяет события.
4. UI получает подготовленное состояние и события через тот же локальный API.
5. Независимо от отображения, отправитель передаёт проверенный обезличенный JSON
   Python-серверу только при наличии сети и действующего согласия.

Зависимости направлены к контрактам. UI не импортирует реализацию локальных сервисов,
backend не импортирует код desktop, ядро не вызывает UI. Сервисы не хранят ссылки
на React-компоненты, DOM, canvas или CSS-классы.

## Публичный API для интерфейса

Под «эндпоинтами» здесь понимается небольшой набор типизированных операций и событий.
Для Electron это preload/IPC; отдельный localhost HTTP-сервер ради UI не требуется.
Транспорт не является частью предметной логики: другой интерфейс может использовать
другой адаптер, сохранив смысл команд и результатов.

Минимальные возможности API, которые предстоит реализовать:

| Возможность | Назначение |
| --- | --- |
| Список накопителей | Получить доступные диски и данные для их выбора; `listDrives()` уже есть |
| Запуск задания | Передать выбранные диски и согласованные параметры; получить идентификатор задания |
| Пауза / продолжение / остановка | Управлять заданием или диском с определённой областью действия команды |
| Снимок состояния | Получить актуальный статус, прогресс и результаты после открытия или перезагрузки UI |
| Подписка на события | Получать обновления, завершение и ошибки; отписка не должна останавливать анализ |
| Получение отчёта | Получить проверенные агрегаты для отображения без чтения рабочей БД |
| Настройки | Прочитать и изменить нагрузку, автозапуск и согласие через проверяемые операции |

Названия будущих методов и схемы запросов фиксируются в контракте при реализации.
UI передаёт намерение пользователя, а не командную строку, SQL или путь к executable.
Нельзя предоставлять универсальные `execute`, `readFile`, `send(channel, payload)`
или произвольный доступ к IPC вместо ограниченных операций.

Авторитетное состояние задания хранится в локальной логике, а не в React.
Перерисовка, смена экрана, размонтирование компонента и перезагрузка renderer
не запускают анализ повторно и не отменяют существующее задание. После подключения
UI восстанавливает отображение из снимка и событий. Выход из всего приложения
обрабатывается отдельно по правилам сохранения прогресса и продолжения по кнопке;
независимость UI не означает работу анализатора после завершения всех процессов.

## Данные и совместимость

- Локальный API, внутренний протокол анализатора и публичный JSON статистики —
  три отдельных контракта. Изменение одного не должно автоматически менять остальные.
- Общие типы и схемы не импортируют React, Electron, C++-реализацию или Python backend.
  Их расположение уточняется при развитии существующих `contracts/` и `electron/bridge.ts`.
- На каждой границе проверяются входные данные, допустимые команды и состояния.
  Ошибки имеют стабильные коды; UI выбирает подпись и оформление. Для согласованного
  `warn` подпись: «файлы схожи, но требуют ручной проверки».
- Счётчики, состав групп и правила подсчёта принадлежат ядру/локальной логике.
  UI может вычислять геометрию диаграммы и форматировать проценты по определённой
  формуле, но не вводит собственное определение дубликата или пустого файла.
- Локальные сведения о дисках не превращаются в сетевой отчёт автоматически.
  Отправитель принимает только выделенный и проверенный публичный отчёт;
  рабочая БД, пути, хеши и внутренние события не пересылаются.
- Ломающие изменения требуют новой версии соответствующего контракта и адаптера
  либо согласованного обновления потребителей. Неизвестная версия вызывает понятную
  ошибку совместимости, а не попытку продолжить с неверной структурой данных.
- Изменение оформления не меняет версию контракта. Изменение алгоритма сравнения
  при неизменном контракте не требует переделки компонентов интерфейса.

## Правила независимой разработки и проверки

Ядро должно собираться и проверяться без Node.js, Electron и работающего сервера.
Backend должен запускаться и проверяться по JSON-примерам без сборки desktop.
UI должен разрабатываться с тестовой реализацией того же API без реального
сканирования дисков; искусственные данные используются только в тестах/режиме разработки.
Общий launcher может запускать несколько сборок для удобства, но не должен быть
единственным способом собрать или проверить каждый компонент.

Перед признанием разделения подтверждённым нужны проверки:

- замена UI при неизменном контракте не требует изменения ядра и backend;
- размонтирование и повторное подключение UI не сбрасывают активное задание;
- UI восстанавливает состояние уже выполняющегося задания через API;
- локальная работа и диаграммы доступны при отключённом Python-сервере и интернете;
- одинаковые контрактные примеры принимаются либо отклоняются всеми потребителями;
- несовместимые версии и некорректные запросы отклоняются без запуска лишних операций;
- отдельные сборки и тесты компонентов не требуют запуска других компонентов.

Эти проверки добавляются по мере реализации соответствующих возможностей.
Факт записи требований в документ не подтверждает их прохождение.
