# Согласие на статистику — этап 2

Основание: `TODO.md` и уточнения пользователя от 2026-10-14. Отказ в приложении
должен быть ненавязчивым; отдельного подтверждения в установщике сейчас нет.
После отзыва подготовленные отчёты сохраняются локально; повторное согласие
разрешает отправку только новых отчётов.

Последующее уточнение пользователя от 2026-10-14 меняет начальное состояние:
отправка включена по умолчанию. Это заменяет прежнее требование о включении
только после явного согласия. Сохранённый отказ продолжает действовать.

## Интерфейс и установка

В «Настройки → Дополнительно» доступен обычный переключатель «Отправлять анонимную
статистику», изначально включённый для нового профиля. Открытие программы,
настроек или сведений о данных не перезаписывает ранее сохранённое решение.
Окон при запуске и подтверждений при выключении нет. Уведомление имеет версию 2;
включение по умолчанию хранится отдельно от явного действия пользователя.
Рядом указана цель — школьный проект; раскрываемый текст перечисляет локальные,
отправляемые и исключённые данные, включая обезличенные данные диаграмм.

NSIS показывает только информационную страницу с прокруткой. Она не содержит
галочки согласия, не записывает настройку и не меняет её при обновлении.
Будущее оформление согласия с лицензией здесь не реализуется. Сам переход далее
не записывает согласие: начальное состояние включается приложением при первом запуске.
Текст `statistics-notice.txt` также включается в resources пакетов всех платформ.
Для Linux выбран tar.gz: `install.sh` показывает уведомление до копирования файлов,
в интерактивном режиме продолжает установку после Enter. Для macOS выбран PKG
с тем же уведомлением на странице Introduction. Отдельного подтверждения согласия
нет. Сборка, установка и границы проверки описаны в [installation.md](installation.md).

## Граница приложения

`contracts/consent.ts` описывает независимый локальный контракт. Через preload
доступны только `getStatisticsConsent()` и
`setStatisticsConsent({ enabled: boolean, noticeVersion: 2 })`.
Main проверяет отправителя IPC, точную форму запроса и версию уведомления.
UI получает решение (`not-decided`, `default-enabled`, `granted`, `declined`) и признак ошибки
сохранения. Хранилище и проверки отправки не зависят от React.

`ConsentService` хранит запись `statistics-consent.json` в `app.getPath('userData')`.
Запись заменяется целиком через временный файл, с flush содержимого перед rename.
При отсутствующем файле создаётся `default-enabled` с новой локальной меткой.
Перед включением запись должна успешно сохраниться. Повреждённая или неподдерживаемая
запись не разрешает отправку и не заменяется значением по умолчанию. Явные решения
версии уведомления 1 сохраняются: состав отправляемых данных не изменён, меняется
только начальная настройка. Main допускает один экземпляр
приложения на профиль, чтобы второй процесс не использовал старое решение из памяти.

Отзыв сначала запрещает отправку в памяти и вызывает `AbortController.abort()`,
затем сохраняется. Если замена файла не удалась, сервис пытается записать отказ
непосредственно в файл. Даже частично записанный JSON при загрузке запрещает отправку.
Удалять запись нельзя: отсутствие файла снова включило бы начальную настройку.
Если и прямая запись невозможна, отправка в текущем процессе остаётся
запрещённой, а UI сообщает, что выбор не сохранён и после перезапуска настройку
надо проверить. При полном отказе записи файловой системы нельзя гарантировать
сохранение отзыва между процессами; успешное сохранение в этом случае не заявляется.

## Подготовленные отчёты

При первой инициализации и новом включении создаётся случайный локальный `grantId`. Повторное включение
уже включённой настройки сохраняет его; после отзыва создаётся другой. Это
служебная метка периода согласия, а не отправляемый идентификатор пользователя.

`prepareReport(report, consent)` проверяет и копирует публичный отчёт, один раз
связывая его с текущим согласием (либо `null`). `savePreparedReport` и
`loadPreparedReport` сохраняют/читают локальную оболочку с этой меткой. Отзыв не
удаляет локальные отчёты и не меняет их метки. Отчёты без метки или со старой меткой
не получают разрешение при последующем согласии. Неподдерживаемые оболочки и старые
JSON без оболочки отклоняются, а не получают новое разрешение автоматически.

`sendReport` принимает только подготовленную оболочку, заново проверяет публичный
JSON и непосредственно перед каждым вызовом транспорта проверяет текущее согласие,
совпадение метки и отсутствие отмены. Транспорту передаются только публичный JSON
и локальный `AbortSignal`, а также случайный номер отчёта для защиты от повторов;
оболочка и метка не отправляются. Транспорт обязан
обрабатывать сигнал отмены. Уже переданные серверу байты отозвать этим нельзя.

Очередь этапа 8 следует этим правилам:

1. Подготовить и сохранить оболочку при создании отчёта.
2. При каждой попытке читать исходную оболочку и вызывать `sendReport` с единственным
   сервисом согласия из main. Не вызывать `prepareReport` заново для старого отчёта.
3. При `false` не отправлять отчёт; оставить локальную копию для результатов.
4. При ошибке транспорта сохранить ту же оболочку для ограниченного повтора.

Очередь и HTTPS-транспорт реализованы; main использует единственный сервис
согласия для IPC и каждой попытки доставки. Подробности конфигурации, ограниченных
повторов, номера отчёта и отдельного статуса: [report-delivery.md](report-delivery.md).
Сценарии отказа, отзыва, недоступности и повторов проверяются на искусственных отчётах.
