## API

`POST https://<домен>/v1/reports`, `Content-Type: application/json` (UTF-8),
`Content-Length`. Клиент этапа 8 также передаёт `Idempotency-Key`: случайный UUID v4
конкретного отчёта, одинаковый во всех его попытках. Тело — непосредственно контракт v1, без локальной оболочки
`consentGrantId` и без дополнительных полей. Сжатие не поддерживается.
Корректные частичные отчёты с `complete=false` тоже принимаются; это свойство
сохраняется и не означает успешное окончание анализа.

| Код | Значение |
| --- | --- |
| 201 | Отчёт принят, включая повтор с тем же UUID: `{"accepted":true,"receipt_id":"<случайный UUID>"}` |
| 400 | Повреждённый JSON, повторные ключи, чрезмерная вложенность, неверный запрос |
| 404 / 405 | Неизвестный адрес / неподдерживаемый метод |
| 409 | Тот же `Idempotency-Key` уже принят с другим JSON |
| 411 | Не указан размер тела |
| 413 | Тело больше 2 097 152 байт |
| 415 | Неподдерживаемый тип содержимого или сжатие |
| 422 | Не пройдена схема v1 или арифметическая проверка |
| 429 | Превышена частота обращений |
| 500 / 502 / 503 / 504 | Ошибка, недоступность, лимит хранения или времени |

Ошибки имеют JSON `{"accepted":false,"error":"<фиксированный код>"}`.
Прокси возвращает общий `request_rejected`, приложение — более точный код.
Некорректный TLS/обрыв соединения не гарантирует HTTP-ответ.
Ответы не содержат входных значений, подробностей валидатора или исключений.
Внутренний `GET /healthz` проверяет доступ к SQLite; снаружи он недоступен.
Публичного чтения/выгрузки/удаления отчётов нет.

`receipt_id` относится к отдельной записи, а не пользователю/устройству.
С заголовком `Idempotency-Key` он совпадает с UUID отчёта. Повтор того же
канонического JSON с тем же UUID возвращает 201 и прежнюю квитанцию; число
записей, квоты и время приёма не меняются. Проверка и вставка атомарны,
повтор при заполненной квоте тоже принимается. Другой JSON под тем же UUID
получает 409. Без заголовка сохраняется совместимость этапа 7: новый серверный
UUID на каждый POST, без дедупликации. Защита действует до удаления записи
по сроку хранения или удаления БД. Клиент ограничивает повторы 24 часами:
[report-delivery.md](report-delivery.md).
Сервер получает данные диаграмм в `statistics.*.types`; C++, Electron и Node
ему не нужны. Локальные диаграммы вычисляются независимо от сервера.

## Лимиты и хранение

| Ресурс | Настройка |
| --- | --- |
| Тело запроса | 2 МиБ; глубина JSON до 16; UTF-8; запрещены NaN/Infinity и повторные ключи |
| Частота | nginx: 6 запросов/мин на IP + burst 3; суммарно 60/мин + burst 10 |
| Лимит приложения | 60/мин, burst 10, один worker; сбрасывается при его перезапуске |
| Соединения | До 2 на IP, до 128 соединений worker nginx, очередь Gunicorn 16 |
| Время | Бюджет приложения 5 с; sync worker Gunicorn прерывается при молчании более 10 с |
| Ожидание сети | Заголовки 5 с; простой чтения тела/отправки 10 с; upstream connect 2 с/read 12 с |
| RAM / CPU | Приёмник 256 МиБ / 0,5 ядра; прокси 128 МиБ / 0,25; очистка 64 МиБ / 0,1 |
| Данные | До 100 000 отчётов и 256 МиБ суммарных JSON |
| SQLite | Файл до 480 МиБ; rollback journal DELETE; без WAL и VACUUM-копии |
| Дисковый бюджет | Менее 1 ГиБ на БД и временный rollback journal при штатной работе |
| Срок | 30 дней от серверного приёма; проверка каждую минуту, даже без запросов |

Очистка удаляет порциями по 100 записей, с бюджетом 10 с за проход; при блокировке
или исчерпании времени продолжает на следующем проходе. После простоя сервиса
истёкшие записи очищаются при запуске. Фактическое удаление имеет задержку
периода очистки и возможного восстановления после ошибок/остановки.
Если SQLite недоступна при запуске очистки, сервис повторяет открытие через
минуту; в журнал попадает только `retention_unavailable`, без текста исключения.
Удалённое содержимое обычной таблицы зануляется `secure_delete=ON`, свободные
страницы переиспользуются. Это не обещание физического стирания на SSD,
в снимках диска, сторонних резервных копиях или swap хоста.

Транзакция `BEGIN IMMEDIATE` атомарно проверяет квоты и сохраняет отчёт;
триггеры учитывают число записей и объём. При переполнении сервер отказывает
новым запросам с 503; актуальные старые отчёты не вытесняются.
`max_page_count` ограничивает размер БД, но не всю файловую систему. Образы,
Docker build cache, исходники и сертификат в бюджет данных не входят.
Квота Docker volume на уровне файловой системы не устанавливается.

Тайм-аут чтения nginx ограничивает **простой между чтениями**, а не полную
длительность медленной загрузки. Зависшая обработка обрывается Gunicorn;
ответ после такого обрыва может быть 502. Лимиты соединений, RAM/CPU и tmpfs
действуют дополнительно. Большой корректный локальный отчёт может не
уложиться в серверные лимиты и получить отказ.

## Приватность и изоляция

SQLite хранит только проверенный JSON, случайный номер записи и серверное время
приёма. IP, User-Agent, cookies, query string и другие заголовки в неё не входят.
Неизвестные поля запрещены общей схемой, счётчики сверяются с группами,
дисками и категориями. Данные файлов дополнительно не запрашиваются.

nginx использует IP непосредственного соединения только в памяти для лимитов;
не доверяет `X-Forwarded-For`. Дополнительная прокси/CDN потребует отдельного
решения о доверии адресам и журналах. Access/error logs nginx и Gunicorn
отключены, включая ошибки парсера HTTP; Docker logging для них тоже отключён.
Диагностика — по состоянию контейнеров и healthcheck. Очистка пишет только
фиксированный `retention_unavailable`, с ротацией 1 МиБ.
Тела в буфере nginx хранятся в tmpfs до завершения запроса; tmpfs ограничен 16 МиБ.

Полная анонимность не обещается: сеть видит IP; политика хостинга, firewall,
Docker daemon, резервных копий и внешнего прокси пока неизвестна. Произвольные
расширения могут содержать пользовательский текст в рамках контракта v1;
схема не определяет его смысл. См. [statistics.md](statistics.md).

Контейнеры работают без root, с read-only root filesystem, без Linux capabilities,
с `no-new-privileges`, лимитами процессов, RAM/CPU и отключёнными core dumps.
Приёмник доступен только во внутренней сети Compose; очистка вообще без сети.
Наружу публикуется только HTTPS-порт отдельного nginx. Конфигурация системного
nginx, Python-пакеты хоста и соседние приложения не меняются.

## Локальный Docker для отладки

По уточнению пользователя адрес контейнера хранится в корневом `.env`.
Запуск из корня проекта (Node.js 24 и работающий Docker с Linux-контейнерами):

```sh
npm run server:dev
npm run server:check
npm run server:stop
```

`server:dev` создаёт `.env` из `.env.example`, если файла ещё нет, собирает
приёмник, создаёт локальный самоподписанный сертификат на 30 дней через OpenSSL
из образа приёмника и запускает отдельный Compose-проект `duprove-debug`.
После запуска проверяет и перечитывает конфигурацию nginx, чтобы обновлённые
заголовки и адрес пересозданного приёмника действовали без удаления контейнера прокси.
OpenSSL на Windows устанавливать не нужно. Актуальный IPv4 HTTPS-прокси
берётся из `docker inspect`, а не из примера или DNS сайта, и записывается
в `DUPROVE_CONTAINER_IP`. После пересоздания контейнера команду следует
выполнить заново: IP может измениться. Остальные строки существующего `.env`
сохраняются; управляемые этой командой параметры локального стенда обновляются.

В `.env` также записываются:

- `DUPROVE_REPORT_URL=https://127.0.0.1:8443/v1/reports` — доступный с Windows
  адрес через опубликованный порт Docker; `DUPROVE_LISTEN` позволяет изменить порт.
- `DUPROVE_TLS_DIR` и `DUPROVE_CA_FILE` — абсолютные пути локального сертификата
  в `.verification/server-dev/tls`.
- `DUPROVE_DEV_PROJECT=duprove-debug` — отдельное имя проекта для отладки.

В Docker Desktop Linux-контейнеры находятся в виртуальной машине; для доступа
с хоста используются опубликованные порты. Поэтому внутренний IP хранится
отдельно от URL Windows-клиента. См. [документацию Docker о сети](https://docs.docker.com/desktop/features/networking/).
Сертификат действителен для `localhost` и `127.0.0.1`; для внутреннего IP
отдельный TLS URL не объявляется. `server:check` читает URL/CA/IP из `.env`,
сверяет IP с Docker и выполняет GET, ожидая штатный 405: отчёт при этом не
сохраняется, проверка сертификата включена. В системное хранилище доверия
сертификат не устанавливается. Локальный приватный ключ доступен контейнеру
через bind mount; это только тестовый ключ, не сертификат рабочего сервера.

`.env` и сертификаты исключены из Git. Команда отладки публикует порт только
на `127.0.0.1`, работает только с именем `duprove-debug`/`duprove-debug-*` и
не настраивает сайт `download.licetvideo.ru`. Непакетированный Electron этапа 8
читает URL и тестовый CA из `.env` при запуске; упакованная программа этот файл
не читает. Детали: [report-delivery.md](report-delivery.md).
`server:stop` останавливает контейнеры и сохраняет данные. Полное удаление
локального стенда выполняется отдельно:

```sh
docker compose --env-file .env -p duprove-debug -f backend/deploy/compose.yaml down --volumes
docker image rm duprove-debug-receiver:local
```

Собственные `.env` и `.verification/server-dev/tls` после этого можно удалить.
При изменённом `DUPROVE_DEV_PROJECT` подставить выбранное имя в команды удаления.

## Установка, остановка, удаление

Нужны Linux с Docker Engine и Compose v2, свободный порт, DNS и действительный
TLS-сертификат для будущего домена. Автоматическое получение сертификата и
изменение DNS не входят в конфигурацию. Базовые образы Python/nginx используют
поддерживаемые теги; версии jsonschema и Gunicorn закреплены в requirements,
транзитивные зависимости разрешаются при сборке.
Для воспроизводимого выпуска следует сохранить digest собранных образов.

Разместить исходники отдельно, например в `/srv/duprove-statistics/app`.
Сборке нужны `backend/` и `contracts/report.schema.json` с сохранением путей.
В `/srv/duprove-statistics/tls` разместить **копии** `fullchain.pem` и `privkey.pem`.
Для обычного rootful Docker: каталог `root:101`, режим 750, файлы `root:101`,
режим 640 (nginx UID/GID 101). При user namespace remapping требуется
соответствующее отображение UID/GID. Общие сертификаты других сервисов
не перемещать. Из каталога проекта:

```sh
export DUPROVE_TLS_DIR=/srv/duprove-statistics/tls
# По умолчанию 127.0.0.1:8443. Публичный порт указывается явно:
export DUPROVE_LISTEN=0.0.0.0:443
docker compose -f backend/deploy/compose.yaml config --quiet
docker compose -f backend/deploy/compose.yaml build receiver
docker compose -f backend/deploy/compose.yaml up -d --no-build --wait
docker compose -f backend/deploy/compose.yaml exec -T proxy nginx -t
docker compose -f backend/deploy/compose.yaml ps
```

Не занимать порт соседнего приложения. Если 443 занят, выбрать отдельный IP/порт
и согласовать HTTPS URL. При совпадении имени проекта `duprove-statistics`
выбрать другое через `-p` **во всех** командах. Образы, контейнеры, сети и том
имеют префикс имени проекта. Не подключать томы других приложений.
TLS-ключи и `.env` не коммитить. После замены копий сертификата:
`docker compose -f backend/deploy/compose.yaml restart proxy`.

Остановка с сохранением данных:

```sh
docker compose -f backend/deploy/compose.yaml stop
```

Удаление контейнеров, сетей и **всех отчётов этого проекта**:

```sh
docker compose -f backend/deploy/compose.yaml down --volumes --remove-orphans
docker image rm duprove-statistics-receiver:local
```

Остаются: отдельная копия исходников, копии сертификата и ключа в выбранном
каталоге, необязательный `.env`, базовые образы `python:3.12-slim`/
`nginx:stable-alpine` и Docker build cache. Удалить собственные исходники/копии
сертификатов при необходимости. Общие образы, Docker и кэш автоматически не
удаляются: ими могут пользоваться другие приложения. Глобальный
`docker system prune` не используется. DNS, firewall и внешние резервные копии
обслуживаются отдельно их владельцем.

## Проверки

```sh
python -m pip install -r backend/requirements.txt
npm run test:backend
npm run test:server
# Docker + openssl, отдельный случайный проект и искусственный сертификат:
npm run test:server:deployment
```

Deployment-тест проверяет реальный TLS с проверкой тестового сертификата,
статусы, лимиты, сохранение после перезапуска, очистку без HTTP-запросов,
принудительное завершение зависшего worker и восстановление приёма,
настройки контейнеров и удаление собственных контейнеров, сетей и тома. Результаты и границы
проверки — в [verification.md](verification.md). CLI проверки stdin сохранён,
см. [backend/README.md](../backend/README.md).
