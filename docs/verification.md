Для дополнительных томов проверены пропуск невыбранного вложенного тома
и дубликаты между двумя явно выбранными корнями. macOS проверяет том с именем
`Macintosh HD` вне `/Volumes`, путь с пробелом и исчезновение после отключения.
На macOS точные счётчики проверяются в созданном тестом каталоге данных:
службы ОС могут создавать собственные Spotlight/fsevent-файлы в корне тома.
На Windows форматируется только новый 128 MiB VHDX, идентифицированный по пути
образа; физические диски не выбираются. Очистка не выполняется рекурсивно,
пока временный том остаётся подключённым.

Первый запуск [38564987412](https://github.com/frdkss/Duprove/actions/runs/38564987412)
прошёл сборку и обычные проверки, но обнаружил ошибки подготовки новых образов:
VHDX был передан Windows как VHD; macOS отклонила создание APFS на 128 MiB.
После исправления формата и перехода на sparse image 1 GiB новые тесты прошли.
В macOS Clang остаётся предупреждение о неиспользуемой локальной lambda `add`
в `drives()`; оно не препятствует сборке и не относится к пути выполнения macOS.

Пункт обнаружения накопителей этапа 3 закрыт. Проверки не заменяют испытания
физического отключения USB, реальных SMB/NFS-серверов, TCC-диалогов или отдельный
стресс-тест системного APFS firmlink дерева. Эти ограничения сохраняются.

Реального Mac в этой среде нет. Код адаптера сверён с API Apple; общая логика
отбора macOS-томов прошла CTest на искусственных данных. Скомпилированный адаптер
macOS, TCC, физические диски, интерфейс Installer и готовый PKG локально **не проверены**.
Конфигурация PKG включает страницу Introduction из общего уведомления и отдельные
цели Intel/Apple Silicon. HTML-ресурс сгенерирован локально.

В `.github/workflows/checks.yml` подготовлены macOS runners обеих архитектур,
проверка настоящего списка томов, сборка PKG, его распаковка через `pkgutil` и запуск
упакованного приложения. Наличие workflow не означает успешный запуск. Developer ID
и notarization не настроены, готового `.pkg` в локальном `release/` нет.
Физические USB-накопители и настоящие NFS/SMB-серверы в этой проверке не использовались.

Подробности: [установка](installation.md), [обнаружение томов](drive-discovery.md).

## Исправление гонки в CI-проверке запуска — 2026-10-14

Основание: [GitHub Actions run 38544336816](https://github.com/frdkss/Duprove/actions/runs/38544336816).
Windows и macOS ARM64 завершились успешно. На macOS Intel прошли сборка, тесты
анализатора, обнаружение системного тома и проверка собранного PKG. Последний
тест окна упал с `Cannot read properties of undefined (reading 'require')`.
Та же ошибка присутствовала в Linux UI-проверке после успешной установки tar.gz.

Тест подключался к inspector во время bootstrap Electron и обращался к
`process.mainModule.require` до появления главного модуля. Теперь он опрашивает
готовность модуля с ограниченным тайм-аутом, затем ждёт приложение и интерфейс.
Ошибки inspector и вызовов приложения не подавляются. В матрице установлено
`fail-fast: false`, чтобы падение одной платформы не отменяло остальные проверки.

Локально: `npm test` — 64/64, включая воспроизведение отсутствующего main module,
ограничение времени ожидания и сохранение ошибок inspector. Исправленный
`tests/packaged-startup.cjs` прошёл на настоящем Linux-пакете через WSLg, вернув
5 томов через preload/main. Результат нового удалённого запуска проверяется отдельно.
