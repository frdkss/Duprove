# Архитектура: этапы 1–2

Основание: локальный `TODO.md` и существующие незакоммиченные заготовки проекта.
Документ описывает реализованные границы и отдельно отмечает незавершённые части.

Обязательные правила дальнейшей разработки и полной замены визуальной части:
[Независимость компонентов](component-boundaries.md). Документ разделяет уже
существующий `listDrives()` и будущий контракт управления анализом; перечисленные
в нём требования не являются заявлением о готовности этих возможностей.

## Компоненты

| Компонент | Ответственность | Зависимости |
| --- | --- | --- |
| `native/duprove-core` | Локальный анализ; статическая C++17 библиотека | SQLite, nlohmann/json, PicoSHA2, адаптер ОС |
| `native/src/platform.*` | Накопители, идентичность файла, категории, исключения ОС | Windows API / Linux filesystem |
| `native/src/traversal.*` | Обход и запись внутренних метаданных | platform, storage, ScanContext |
| `native/src/comparison.*` | SHA-256, побайтовое сравнение, проверка актуальности метаданных | Только локальные файлы и ScanContext |
| `native/src/content.h` | Интерфейс дополнительного сравнения содержимого | Будущие реализации после определения критериев `warn` |
| `native/src/scanner.*` | Отбор по размеру и последовательность стадий | traversal, comparison, report |
| `native/src/storage.h` | Локальный SQLite-индекс, пути, хеши, метаданные | Не используется сервером и транспортом |
| `native/src/report.*` | Агрегация и явная сборка разрешённых полей | Только проекции счётчиков из storage |
| `native/src/main.cpp` | CLI и локальный NDJSON | duprove-core; stdout, stdin |
| `electron/services/analyzer-service.ts` | Запуск native CLI, проверка результата | Node child_process; общий контракт |
| `electron/services/report-service.ts` | Проверка JSON и текущего согласия перед передачей | Внедряемый транспорт; без адреса и сетевой реализации |
| `electron/services/consent-service.ts` | Сохранение решения, периоды согласия и отмена отправок | Локальный JSON; независим от UI и ядра |
| `src/` | React UI: локальные данные и отображение | Узкий preload API; без Node и доступа к сети |
| `backend/duprove_backend/` | Независимая граница приёма и проверки статистики | Python + общая схема; без зависимости от ядра/UI |
| `contracts/` | Схема, TS-типы, инварианты и искусственные примеры | Общие для клиента и сервера |

`ScanContext` передаётся явно: управление и callback прогресса больше не являются
глобальными переменными или зависимостями от executable. CTest линкует библиотеку
без `main.cpp`; экземпляры контекста независимы. Ядро не знает о React, Electron,
сервере, HTTP, согласии на отправку и пользовательских уведомлениях.

## Два канала данных

Локально: React → preload → Electron main → C++ CLI. Запрос `--drives` возвращает
локальные пути, имена и ёмкости. Эти сведения нужны для выбора накопителей.
В UI реализованы получение списка, выбор дисков, обзор ёмкости, панель режимов,
настройки темы и справка. Выбор нагрузки пока сохраняется только как предпочтение.

Локальный CLI `--job <file.json>` принимает `roots` (1–64 абсолютных пути),
`database` (путь собственного рабочего SQLite), `load` (0–2), `content` (false).
Это внутренний формат, **не** контракт отправки. Строки stdin:
`{"action":"pause|resume|stop","disk":0}` и `{"action":"load","value":0}`.
stdout содержит NDJSON-события `progress`, `result`, `error`.
`progress.disks` и `result.disks` содержат локальные пути. Их нельзя журналировать,
сохранять как статистику или отправлять. `result.report` выделяется функцией
`reportFromEvent`, проверяется общей схемой и арифметическими инвариантами.
В ошибки клиентской границы попадают только фиксированные коды.

Публично: `report` → валидатор → локальная оболочка периода согласия → проверка
актуального согласия и метки перед каждой попыткой → `ReportTransport`.
Транспорт получает только публичный JSON. Отчёты прежнего периода согласия после
отзыва остаются локально и больше не отправляются. Контракт, хранение и ограничения:
[Согласие на статистику](consent.md).
По последнему уточнению пользователя новый профиль использует `default-enabled`;
он разрешает отправку, но отличается от явного `granted`. Сохранённый `declined`
не меняется, включая записи предыдущей версии уведомления.
Сетевой транспорт будет реализован в этапе 8; сервер HTTP/HTTPS, хранение,
ограничения запросов и развёртывание — в этапе 7. Сейчас backend можно отдельно
запустить как проверяющий stdin JSON процесс. Его отключение не затрагивает
обход, сравнение, отчёт и UI. Нет автоматических отправок или фоновых запросов.

Схема и определения счётчиков: [contracts/README.md](../contracts/README.md).
Обе стороны отклоняют дополнительные поля; транспорт не получает рабочую БД
или внутреннее событие целиком. Runtime-схема определяет форму данных; TS-интерфейсы
дают подсказки компилятора, но не заменяют проверку входных данных.

## Состояние прототипа и открытые решения

Прототип уровней 1–3 сохранён и разделён на модули. Он отбирает непустые файлы
по размеру, хеширует кандидатов и проверяет совпавшие хеши побайтово; имя и дата
не используются для отсева. Это текущее поведение кода, а не закрытие всех вопросов
этапа 0 или подтверждение готовности этапов 3–4.

Ранее заготовка при `content=true` нормализовала пробелы в `.txt`. Это не реализует
согласованное полное совпадение содержимого и не определяет работу с картинками.
Автоматическое применение этого несогласованного правила удалено; `content=true`
пока отклоняется. Для будущей реализации выделен `ContentComparator`, результаты
которого не должны превращаться в точные дубликаты. Формат `warn` остаётся открытым.

В заготовке лишние копии относились к дискам через произвольный выбор первого
экземпляра. Теперь глобальный `N - 1` и локальные участники/группы разделены.
Распределение лишних копий по дискам/категориям остаётся открытым вопросом этапа 0.

Не завершены: безопасный обход всех пограничных случаев, сохранение/возобновление
прогресса с гарантиями, очистка рабочего файла по порогу 5 МБ, реальные ограничения
нагрузки, планировщик очереди и сетевой транспорт, диаграммы, трей, уведомления,
полный цикл установки. Согласие и защита подготовленных отчётов реализованы в этапе 2.
Процент старого прототипа относится к фазам, а не к достоверной общей оценке времени.
Не использовать каркас как готовый массовый анализатор; проверки этапа 1 работают
только с искусственными наборами. Поиск дубликатов на реальных дисках здесь не запускался.

## Оформление и UI

Оформление реализовано по трём изображениям пользователя: светлая зелёная боковая
панель, диски с круговой диаграммой, раскрываемые режимы и четыре группы настроек.
Системный стек шрифтов из ветки `website` сохранён; Tailwind и удалённые шрифты
не требуются. Временный векторный логотип-лист находится в `public/logo.svg`.
Каждый элемент находится в своей папке с отдельными TSX/CSS;
созданы каталоги `components`, `window`, `popup`, `modal`.
Есть модальное окно справки. Диаграмма отображает состояние до начала анализа,
без выдуманных процентов или счётчиков. Выбор темы и нагрузки сохраняется локально.
Согласие доступно в настройках и сохраняется через main; при запуске нет диалога,
при отзыве нет подтверждения. Действующее сканирование и его настройки ещё не
реализованы; их элементы отключены. Окно без системной рамки имеет собственную перетаскиваемую строку
заголовка и три кнопки. Узкий IPC `duprove:window` принимает только minimize,
maximize и close от главного фрейма своего окна. Renderer работает с context isolation и sandbox.
Основание для preload API: https://www.electronjs.org/docs/latest/tutorial/context-isolation
