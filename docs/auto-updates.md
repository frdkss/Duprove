# Канал обновлений, этап 10

Основание: код установщиков, локальные проверки и проверка GitHub API от
2026-10-29. Полный переход через опубликованные GitHub Releases **ещё не
подтверждён**. Это описание реализации и её границ. Результаты — `verification.md`.

На дату проверки опубликован `v2.0.0`, но его assets не содержат обязательного
`stable.json`; прямой GET возвращает HTTP 404. Реальный `GithubUpdateTransport`
с условной текущей версией 1.9.9 завершил проверку со статусом `UPDATE_FAILED`,
не начиная установку. Это сетевой тест с имитацией старой версии клиента,
а не обновление установленной программы.

Последний workflow [40161461692](https://github.com/frdkss/Duprove/actions/runs/40161461692)
остановился на Windows-тесте helper, публикация пропущена. Ожидаемый сценарий
отката завершал helper кодом 1, который GitHub Actions ошибочно принимал за итог
успешного теста. В локальном `tests/test_update_windows.ps1` добавлен явный успешный
выход после проверок и очистки; тест с оболочкой GitHub Actions теперь проходит.
Изменение ещё не опубликовано в репозитории. В удалённых `main` и теге `v2.0.0`
`package.json` всё ещё содержит 1.0.0, в текущем рабочем дереве — 2.0.0.

Дополнительно воспроизведено завершение прямо запущенного Windows helper после
выхода родителя. Запуск изменён на короткий PowerShell bootstrap с `Start-Process
-WindowStyle Hidden`; пути передаются через окружение и не подставляются в код.
Отдельный тест подтверждает продолжение helper после настоящего `process.exit()`.
Локальный переход двух изолированных NSIS-пакетов 1.0.0 → 1.0.1 после исправления
успешен: новый процесс подтвердил запуск, сохранённый отказ от статистики и
тестовый отчёт сохранились. Окружение NSIS-теста очищено от `ELECTRON_RUN_AS_NODE`,
который запускал тестовую GUI-программу как Node.js и приводил к откату.
Это проверка установки локального пакета; получение и установка следующего
реального выпуска через GitHub пока не проверены.

## Компоненты и канал

`electron/services/update-service.ts` — отдельный локальный сервис; он не зависит
от React, Python, отчётов и согласия. Main предоставляет UI только `getUpdate`
и `onUpdate` со статусом, версией, процентом, сроками и фиксированным кодом ошибки.
Renderer не передаёт адрес, путь к пакету или команду установки.

Источник фиксирован: `https://api.github.com/repos/frdkss/Duprove/releases?per_page=10`.
Проверяются последние десять релизов, сортируются по числовой версии, исключаются
draft, prerelease, теги кроме `vX.Y.Z`, текущая и более старые версии. Для каждой
кандидатной версии загружается подписанный `stable.json`; выбирается самая новая
совместимая. Неизвестный формат/подпись останавливает попытку. Наличие старого
совместимого релиза за пределами этих десяти не гарантируется.

Проверка запускается после готовности окна, с учётом сохранённого ограничения
частоты. Нормальный интервал — 6 часов. После ошибок: 1 мин, 5 мин, 30 мин,
6 ч, далее не чаще раза в сутки. Срок и число ошибок записываются до запросов и
сохраняются между запусками. Нет отдельного запроса для определения интернета;
сетевой сбой обрабатывается как неудачная попытка. Анализ продолжает работать.

## Подлинность и совместимость

`stable.json` содержит `payload` (base64 точных байтов JSON) и `signature`
(Ed25519). В payload входят `schema:1`, `channel:stable`, версия, `dataSchema:1`
и цели: ОС, архитектура, формат установки, минимальная версия ОС/glibc, точное
имя asset, размер, SHA-512. Размер metadata ограничен 64 КиБ, пакета — 1 ГиБ.
Подпись проверяется до использования метаданных, хеш и размер — после загрузки
и перед подготовкой установки; Windows-helper повторяет хеш перед запуском.
Неподписанный/изменённый пакет не запускается. SHA-512SUMS для ручной проверки
не заменяет подпись `stable.json`.

Публичный ключ `config/update-public-key.pem` встроен в main при сборке. Его
нельзя заменить через `.env`, настройки UI или сетевой ответ. Новый постоянный
ключ создан по ответу пользователя 2026-10-15. Закрытый PKCS8 хранится локально
в `.tools/release-signing/private.pem` (игнорируется Git; ACL текущего пользователя)
и добавлен как Actions repository secret `DUPROVE_UPDATE_PRIVATE_KEY`. Значение
ключа не выводилось в журналы. Ключ нельзя создавать заново при каждом релизе.
Ротация потребует переходного выпуска; автоматического доверия новому ключу нет.

Текущий подписывающий скрипт выпускает цели:

| Цель | Минимум в metadata | Установка |
| --- | --- | --- |
| Windows x64 | 10.0.19045 | NSIS для текущего пользователя |
| Linux x64 | ядро 5.15.0, glibc 2.35 | tar.gz, установленный через install.sh без sudo |

Это консервативные ограничения канала, а не утверждение о проверке всех таких ОС.
Изменение нижней границы требует реального запуска на целевой системе. Windows
7/8, musl, чужая архитектура, другой формат, другой `dataSchema` не получают
этот пакет. Отдельного legacy-канала пока нет, совместимость с прежними ОС не
объявляется. Windows ARM64/Linux ARM64 не публикуются этим workflow. macOS
PKG/DMG публикуются для первоначального скачивания, автоустановка для них
**не реализована**. В development, распакованной Windows-сборке, Linux-архиве без
`install.sh`, системной/чужой установке обновления отключены.

HTTPS использует проверку сертификата и TLS >= 1.2. Разрешены только GitHub и
его asset-хосты; максимум четыре перенаправления. Нет авторизации, постоянного
ID клиента, тела запроса, отчётов, имён/путей пользователя; только фиксированные
GET, User-Agent и Accept. GitHub как получатель видит IP соединения. Проверка
metadata ограничена минутой, скачивание — 15 минутами, простой сокета — 30 с.
Частичная загрузка удаляется, следующая попытка скачивает заново.

## Установка, данные и восстановление

Загрузка может идти одновременно с анализом. Установка ждёт завершения или
остановки: состояния running, paused, stopping и находящаяся в обработке команда
анализа блокируют её. Когда приложение свободно, UI и системное уведомление
предупреждают о перезапуске за минуту. Если начать/продолжить анализ, отсчёт
сбрасывается. На границе установки main синхронно блокирует новые команды,
готовит независимый helper, ждёт его подтверждения и штатно завершает worker
и доставку отчётов. Неудачный запуск helper не закрывает приложение.

NSIS добавляет `.duprove-managed` только пользовательской установке. Helper
PowerShell работает вне заменяемого каталога, делает резервную копию приложения,
ждёт завершения старого процесса, вызывает `/S --updated /currentuser /D=...`
и запускает новый executable. UAC/повышение прав отключены. При ненулевом коде
установщика или неудачном запуске восстанавливает файлы и запускает прежнюю
версию. Полное восстановление записей установщика в реестре и отказ питания
посреди NSIS пока не подтверждены; это ограничение Windows-восстановления.

Linux-helper работает без root: создаёт соседний каталог, блокирует параллельную
транзакцию, сохраняет текущую установку как `.previous`, заменяет каталог и
запускает приложение. При сбое возвращает прежний каталог. Launcher `install.sh`
восстанавливает отмеченный `.previous`, если отключение питания пришлось на
промежуток между переименованиями и основной каталог отсутствует. Прерывание
после второго переименования и повреждение диска пока не проверены.

Новая версия подтверждает старт после worker, загрузки UI и, для обновлённого
запуска, проверки доступности анализатора. Helper ждёт до 120 с; без подтверждения
выполняет откат. Версия с записанным неудачным результатом блокируется локально,
чтобы не возникал цикл установки. Сбой файловой системы при самом откате может
потребовать ручного восстановления; безусловная гарантия восстановления отсутствует.

`userData` и каталог приложения разделены; helper отказывает, если профиль
оказался внутри заменяемого каталога. Согласие, UI-настройки, отчёты и SQLite
незавершённого анализа не удаляются. В этом выпуске их форматы не менялись.
Переход с другим `dataSchema` отклоняется: реальная миграция должна быть добавлена
и проверена вместе с будущим изменением формата, а не выполняться предположительно.

## Выпуск и сайт

`.github/workflows/release.yml` запускается при push в `main` (включая слияние PR),
при push тега `vX.Y.Z` или вручную для `main`. Версия берётся из `package.json`;
новый тег создаётся при публикации на точном коммите сборки. Если стабильный
релиз этой версии уже опубликован, повторный push пропускает публикацию.
Для следующего выпуска нужно увеличить версию (`npm version patch --no-git-tag-version`
обновляет также lockfile). Тег, указывающий на другой коммит, несовпадающая
версия тега и существующий незавершённый draft приводят к явной ошибке.
Push в `future/duprove_v.1.0` запускает проверки, но сам по себе не выпускает
стабильную версию: правка workflow должна попасть в `main`.

Workflow собирает Windows x64, Linux x64, macOS Intel и
Apple Silicon, выполняет проверки. Финальная задача в environment `release`
получает installers, проверяет совпадение закрытого ключа с публичным, создаёт
`stable.json` и `SHA512SUMS`, загружает всё в draft и только затем публикует
стабильный release. При ошибке draft остаётся неопубликованным. Уже существующий
тег не перезаписывается. Приватный ключ доступен только задаче подписи.
Тег из подготовительной задачи явно передаётся подписывающему скрипту, поэтому
сборка из ветки `main` не ошибается из-за `GITHUB_REF_NAME=main`. Выпуски
сериализованы одной concurrency-группой, включая push ветки, тега и ручной запуск.

Сайт в ветке `website` уже использует тот же `frdkss/Duprove`, исключает
draft/prerelease и выбирает `.exe`/`.tar.gz`. Имена установщиков сохранены;
`stable.json` и `SHA512SUMS` не совпадают с его фильтром установщиков.
Ветка сайта не изменялась. PKG/DMG существующий фильтр сайта не показывает;
это отдельное незавершённое согласование macOS-загрузок, не поддержка автообновлений.

Опубликованный `v2.0.0` пока не является доступной целью автообновления из-за
отсутствующего `stable.json`. Следующий выпуск должен иметь увеличенную версию
в `package.json` и lockfile, соответствующий тег `vX.Y.Z`, установщики и подписанный
`stable.json`, созданный постоянным ключом. Одной загрузки `.exe` недостаточно.
Старые приложения без сервиса обновления не могут получить его автоматически.
Сквозной тест через GitHub требует двух реальных установочных выпусков с сервисом
обновления и доступного подписанного metadata для целевой версии.

Команды локальной проверки:

```text
npm run build
npm test
npm run test:desktop
npm run test:ui
powershell -NoProfile -ExecutionPolicy Bypass -File tests/test_update_windows.ps1
python tests/test_update_linux.py
node tests/update-nsis.cjs
```

Последняя команда — отдельная Windows-проверка двух настоящих NSIS-сборок с
уникальными appId, профилем и каталогом; не публикует релизы и не заменяет
обычную установку Duprove. Linux-тест helper использует искусственные executable;
его нельзя считать проверкой полного tar.gz-приложения через GitHub.

Справочные первичные источники:
[цели electron-updater v26](https://www.electron.build/v26/docs/features/auto-update/),
[GitHub Releases API](https://docs.github.com/en/rest/releases/releases),
[GitHub Actions Secrets API](https://docs.github.com/en/rest/actions/secrets).
