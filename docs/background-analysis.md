## Запуск и состояние

React вызывает только `DesktopBridge`. Контракт `contracts/analysis.ts` v1
содержит запуск, команды задания, снимок и события. Произвольные пути принимаются
только при совпадении со списком накопителей, полученным main. CLI и рабочая БД
недоступны renderer. Чужой frame, неверная версия, параметры, состояние команды
и второй одновременный запуск отклоняются.

`JobClient` держит небольшой снимок в Electron main. `JobService` в Node worker
запускает отдельный C++-процесс, разбирает ограниченный NDJSON, валидирует отчёт
и сохраняет данные. Обработка больших результатов и синхронизация файлов
не выполняются в обработчике запроса состояния. Один worker задания запускает
анализатор; в высоком режиме SHA-256 и проверка кэшированных хешей распределяются
по рабочим потокам. Выбранные диски обслуживаются последовательно;
междисковые кандидаты сравниваются после общего обхода.

`getAnalysis()`, `startAnalysis()`, `controlAnalysis()`, `onAnalysis()` и
`getAnalysisReport()` не зависят от React. Переподключение UI получает снимок;
отписка не останавливает задание. Пауза, продолжение и остановка относятся ко
всему заданию: отдельная пауза диска может блокировать междисковое сравнение и
в этой версии не предоставляется UI. Режим и дополнительное содержание выбираются
до запуска. Остановка ждёт сохранения, через 5 секунд завершает зависший процесс;
следующее продолжение повторит незавершённую работу.

## Сохранение и актуальность

В `userData/analysis/` находятся атомарно заменяемый `job.json`, служебный
`input.json`, `work/index.sqlite`, локальный `content.json` и отдельные
`reports/<job-id>.json`. Весь каталог анализа исключён из обхода. Пути, имена,
identity, mtime/ctime и хеши остаются в локальном индексе. Отчёт сохраняется в
проверенном конверте с действующим идентификатором согласия; сеть этапа 5
не используется. Отзыв согласия не меняет локальный анализ.

SQLite использует `synchronous=FULL`, журнал DELETE, кэш 16/32/64 МиБ по режиму
и временные таблицы на диске. Обход сбрасывает транзакцию каждые 1024 записи,
хеширование — каждые 512/1024/2048 файлов либо после 1 секунды на границе файла.
Это уменьшает число дорогих синхронизаций мелких записей. При аварии сохраняются
зафиксированные файлы; текущий файл/незафиксированная порция повторяются.
Побайтовое сравнение также фиксирует группы порциями 512/1024/2048 файлов
либо после секунды на границе файла, вместо прежних 256 файлов.

После перезапуска незавершённое задание получает `interrupted`, без автоматического
продолжения. Кнопка продолжения сохраняет ID задания, заново обходит дерево,
учитывает новые/удалённые файлы и повторно проверяет identity, размер, mtime и
ctime перед использованием сохранённого SHA-256. Побайтовое сравнение, состав
групп и проверка содержания выполняются заново. Это продолжение по контрольным
точкам файлов, а не сохранение позиции внутри файла или состояния декодера.
Повторная проверка перед отчётом исключает изменившиеся подтверждённые совпадения.
Кэшированные хеши проверяются по актуальным метаданным один раз перед сохранением
в текущий индекс. На Windows при последовательном хешировании соседних файлов
используется одна открытая цепочка родительских каталогов: все компоненты остаются
защищены от переименования/подмены через отсутствие `FILE_SHARE_DELETE`.
У каждого файла отдельно проверяются identity, размер, mtime и ctime. На POSIX
цепочка открывается заново, поскольку дескриптор каталога не запрещает его перенос.
При переходе между каталогами обхода и хеширования Windows переиспользует
защищённую общую часть цепочки. Новый объект владеет этими дескрипторами
самостоятельно; закрытие предыдущего объекта не снимает защиту родителей.
Хеширование байтов в Windows использует системный SHA-256 CNG, в остальных ОС —
прежнюю переносимую реализацию. Формат хеша и проверка старого кэша сохранены.
Лимиты чтения, пауза и остановка проверяются между блоками по 256 КиБ.
Побайтовая проверка в Windows использует две независимые закреплённые цепочки
родителей (для текущего файла и кандидата). Проверки метаданных и чтение
переиспользуют их; файлы и финальная проверка идут в порядке путей. Состояние
самих файлов не кэшируется: identity, размер, mtime и ctime считываются заново.
Запрос кандидатов SQLite подготовлен один раз и повторно связывает параметры.
Файлы с уникальным сочетанием SHA-256 и размера больше не проходят повторный
побайтовый этап; совпадающие хеши обязательно подтверждаются сравнением байтов.
При этом одинаковый размер по-прежнему является необходимым условием хеширования.
Файловая система, не обеспечивающая надёжность identity/времён изменения,
не даёт гарантий против незаметного изменения этих метаданных.

Точный порог рабочего файла: **5 242 880 байт (5 МиБ)**. После успешного результата,
записанного отчёта и закрытия анализатора более крупный `.sqlite` удаляется;
меньший или равный порогу остаётся как кэш. При ошибке, остановке или аварии
очистка не выполняется. Повреждённое состояние не запускает работу автоматически.
Следовательно, после успешного удаления большого индекса сохранённых хешей для
следующего запуска нет. Это действующее правило очистки, а не неисправность кэша.

## Проценты и счётчики

Под диаграммой показывается общий процент выполнения анализа выбранного диска
по этапам (`overall_percent`). Четыре этапа имеют равный вес: обход, SHA-256,
побайтовое сравнение, финальная проверка. При включённой проверке содержания
добавляются два этапа: извлечение и сравнение содержания; всего шесть.
Это доля выполненных этапов с учётом известного прогресса внутри них,
а не доля прошедшего времени и не прогноз оставшегося времени.

При обходе показывается **оценка**: обработанные каталоги / все найденные
каталоги, не выше 99% этапа до завершения обхода. Знаменатель растёт при
обнаружении новых каталогов, поэтому оценка не равна точной доле файлов
или времени. Общий процент сохраняет достигнутый максимум и может временно
не расти при расширении дерева; фактические счётчики продолжают обновляться.
После обхода засчитывается первый этап. В остальных фазах учитывается
`percent` ядра по формулам ниже. В операциях с неизвестным объёмом
число сохраняет уже завершённые этапы. Ожидание другого диска не обнуляет
его прогресс, переходы между фазами не уменьшают процент; **100%** означает
завершение обработки с итоговым отчётом, включая завершение с ошибками отдельных
файлов. Ошибки не оставляют прогресс на 99,99%; статус и неполнота результата
при этом сохраняются. Остановка и авария без результата не получают 100%.
Значение сохраняется вместе со снимком задания.
Ручное возобновление после остановки начинает повторную проверку дерева с 0%.
Старые сохранённые снимки без `overall_percent` также принимаются.

| Фаза | Расчёт |
| --- | --- |
| Ожидание | Сохраняются завершённые этапы |
| Обход и метаданные | Оценка по обработанным / найденным каталогам, до 99% этапа |
| SHA-256 | Обработанный объём кандидатов / их известный суммарный размер; проверенный кэш и попытки обработки недоступных файлов засчитываются, реально прочитанные байты считаются отдельно |
| Побайтовое сравнение | Завершённые файлы-кандидаты / все хешированные кандидаты данного диска |
| Извлечение содержания | Завершённые записи / все обнаруженные файлы диска, включая явные пропуски |
| Сравнение содержания | Завершённые внешние кандидаты / все готовые кандидаты; число пар и стоимость отдельных кандидатов могут различаться |
| Финальная актуальность | Проверенные записи / число участников точных групп плюс записи содержания, если оно включено |
| Завершено | 100% |

Исходное поле `percent` ядра по-прежнему относится к отдельной фазе;
сервис задания преобразует его в общий процент для интерфейса. Отображаются
до двух десятичных знаков; 100% не округляется из незавершённого этапа.
Построение итогового отчёта остаётся в фазе проверки до его завершения.
Во время чтения больших файлов ядро выдаёт состояние примерно каждые 250 мс.
Блокирующий системный вызов или декодер может задержать событие, но main продолжает
отдавать последний снимок. Ошибка одного диска не отменяет проверку остальных;
итог помечается неполным. Дубликаты во время сравнения предварительны до финальной
проверки актуальности.

Локальное поле `work` передаёт операцию, текущий путь, обработанное и полное
количество единиц (каталоги, байты или файлы), реальные байты чтения и для
SHA-256 — завершённые файлы / кандидаты. Эти пути не входят в публичный отчёт.
Для SHA-256 отдельно показываются число принятых кэшированных хешей и реально
прочитанный объём. Скорость с подписью «Обработка» включает объём файлов из кэша;
она не является скоростью физического диска. Единицы КиБ/с и МиБ/с — байты,
не биты. Скорость на большом количестве мелких файлов зависит от метаданных
и задержек открытия, даже если чтение содержимого отсутствует.
SQLite progress handler также публикует состояние во время долгих запросов,
не выполняя вложенных запросов; в нём учитывается пауза. Блокирующий ввод-вывод
остаётся ограничением. Пересчёт предварительных групп ограничен разом в 2 секунды.

Скорость вычисляется в worker по окну последних примерно 15 секунд, после
как минимум 3 секунд измерения. Пауза и смена операции сбрасывают замер.
Оставшееся время этапа — оставшийся объём / скорость. Во время обхода это
оценка для известного фронта каталогов, который ещё может увеличиться.
После обхода показывается также **грубая оценка** всех оставшихся этапов диска:
пока стоимость будущих этапов неизвестна, каждый считается равным по длительности
текущему полному этапу. Это явное предположение, а не измерение будущей работы;
прогноз пересчитывается при смене фаз и может существенно меняться.
Во время обхода общий срок ещё не выводится.

Если 15 секунд нет новых событий, интерфейс показывает отсутствие ответа.
Если события приходят, но путь, обработанное количество и чтение не изменяются
30 секунд, показывает отсутствие продвижения и текущую операцию. Это не
автоматическое признание ошибки: длительный запрос может быть рабочим.
Устаревший прогноз времени скрывается, кнопка остановки остаётся доступной.

В центре бублика — участники точных групп на этом диске, ниже обычным шрифтом —
пустые файлы. Группы считаются отдельно. Число лишних копий `Σ(N − 1)` выводится
для всего задания, без назначения оригинала. Диаграмма строится от всех
учтённых файлов конкретного диска. Каждое расширение имеет отдельный сектор,
включая редкие и составные расширения; объединения в «Другие типы» нет.
Пустые файлы и файлы без расширения имеют отдельные категории. Цвет вычисляется
детерминированно из расширения, независимо от количества, диска и порядка входных
счётчиков; для пустых файлов и файлов без расширения заданы постоянные цвета.
Сектора и легенда упорядочены по расширению. Легенда находится в левой колонке,
показывает количество и долю файлов и перелистывается по восемь
типов, при этом все сектора всегда присутствуют на диаграмме. Наведение и фокус
на секторе или пункте легенды показывают точное расширение, количество и долю.
В статистике по-прежнему сохраняются исходные расширения, без категории «Другие».
Ядро также сохраняет длинные расширения и расширения с Unicode, `_`, `+`;
прежний резервный тип `other` для них больше не создаётся. Старые агрегаты
`other` нельзя восстановить в отдельные расширения без повторного обхода.
`warn` показывает число схожих пар и текст
«Файлы схожи, но требуют ручной проверки»; эти пары не добавляются к дубликатам.
Обзор диска занимает доступную высоту без прокрутки: заголовок и подписи
сохраняют место, диаметр диаграммы подстраивается под оставшуюся область.

## Режимы нагрузки

Параметры реализации, проверяемые на искусственных данных:

| Режим | Чтение, МиБ/с | Цель CPU, доля одного ядра | Бюджет размеров буферов, МиБ | Предел процесса, МиБ |
| --- | ---: | ---: | ---: | ---: |
| Низкий | 64 | 60% | 32 | 512 |
| Средний | 256 | 85% | 64 | 1024 |
| Высокий | Без искусственного предела | Без CPU-пауз, параллельный SHA-256 | 128 | 2048 |

В низком и среднем режимах чтение ограничено общим регулятором SHA-256, побайтовой и дополнительной проверок,
с порцией не более 512 КиБ. Это логически прочитанные байты, включая кэш ОС;
метаданные файловой системы и записи SQLite не входят в этот счётчик.
Регулятор допускает запас чтения на 20 мс: небольшие файлы не вызывают отдельную
задержку на каждый запрос, а время вычисления и самого чтения засчитывается
в лимит. Это верхние пределы, не обещанная скорость накопителя.
CPU ограничивается кооперативными задержками по процессорному времени, а не
жёсткой квотой планировщика: внутри декодера, SQL или построения отчёта допустимы
короткие всплески. Низкий режим использует фоновый приоритет: Windows
`BELOW_NORMAL_PRIORITY_CLASS`, Linux/macOS `nice=10`. Средний и высокий используют
Windows `NORMAL_PRIORITY_CLASS`, на Linux/macOS — соответственно `nice=5/0`.
Высокий режим не запрашивает
администраторские права. В Windows используется высокоточный waitable timer.

В высоком режиме число потоков SHA-256 равно меньшему из числа логических процессоров,
числа файлов-кандидатов и 16. Предел 16 оставляет запас для стеков и арен аллокатора
в пределах 2 ГиБ, включая Linux `RLIMIT_AS`. Каждый поток держит буфер 256 КиБ,
собственный SHA-256 и защищённую цепочку каталогов. В очереди и работе вместе — не
более двух файлов на поток. SQLite и события интерфейса обслуживает только главный
поток анализатора; счётчики чтения передаются через атомарную переменную. Пауза и
остановка проверяются между блоками чтения. При смене режима командой CLI текущая
ограниченная очередь завершается, после чего применяется новый режим; UI выбирает
режим до запуска. Число потоков также учитывает исходный предел памяти процесса.
Обход, побайтовое сравнение и построение отчёта остаются последовательными.
100% CPU не гарантируется: загрузка зависит от накопителя, количества кандидатов
и текущей фазы. Потоки не создают искусственную работу ради показателя загрузки.

Бюджет буферов определяет размеры входа и декодирования, **не общий RSS**:
текст/XML — 0,25/0,5/1 МиБ, вход DOCX/изображений и распакованный ZIP — 4/8/16 МиБ,
изображение — 0,5/1/2 мегапикселя (в двоичном счёте), лимит JPEG — 8/16/32 МиБ.
Превышение даёт `limit`, число таких пропусков видно в UI. Снижение нагрузки
может уменьшать охват дополнительного содержания; точная побайтовая проверка
не ограничивает размер файла. Индекс, DOM и итоговые группы требуют памяти
сверх выделенных входных буферов.

Windows ограничивает commit анализатора через Job Object; Linux — адресное
пространство через `RLIMIT_AS`; macOS контролирует RSS каждые 25 мс, поэтому
возможен краткий выход за порог между измерениями. В macOS используется отдельный
поток наблюдения, кроме потока команд. Достижение предела может прервать задание,
оставив контрольные точки. Node worker имеет предел старого поколения V8 256 МиБ,
одна строка NDJSON ограничена 32 МиБ; очень большой итоговый отчёт завершается
явной ошибкой, а не обещанием неограниченного масштабирования.

## Окно, трей, автозапуск

Статус завершения в диаграмме и под процентом открывает модальное окно
«Журнал анализа». Оно показывает итог выбранного диска, счётчики, режим,
проблемы по этапам без имён и путей файлов. Закрытие — кнопкой или Esc,
фокус возвращается к статусу; длинный журнал прокручивается внутри окна.

Локальный `DiskProgress.issues` содержит код причины, операцию, число событий
без примеров путей (изменение этапа 6). Максимум 16 записей на диск;
счётчик всех ошибок сохраняется независимо от этого ограничения.
Старые примеры удаляются при восстановлении, а текущий путь сохраняется только
в оперативном прогрессе, без записи в `job.json`. Для ошибок чтения, которые низкоуровневый API
не различает, журнал сообщает «файл недоступен или изменился», не выдумывая
конкретную причину отказа ОС. Диагностика не входит в публичный отчёт.
Старые снимки без `issues` читаются; журнал прямо сообщает об отсутствии
подробностей. Сохранённое завершение с ошибками и проверенным итоговым отчётом
восстанавливается как завершённая обработка с 100%, сохраняя признак ошибок.
Кнопка повторного запуска остановленного/прерванного задания называется
«Повторить»; она сохраняет прежнюю семантику возобновления с проверкой кэша.
При новом обходе `.pytest_cache`, как и `.git`, исключается до запроса метаданных.
Старый журнал не переписывается: для результата с новым правилом нужен повтор.

Крестик при `running`, `paused` или `stopping` скрывает окно и оставляет задание
в трее. Клик по значку/«Открыть Duprove» возвращает то же окно. «Выйти и сохранить
прогресс» останавливает задание перед выходом. При неактивном задании крестик
закрывает приложение. Если создать Tray не удалось, окно остаётся доступным.
После успешного завершения скрытого задания запрашивается системное уведомление,
окно автоматически не открывается. Доставка зависит от настроек ОС; в частности,
[Electron требует подписи приложения для уведомлений macOS](https://www.electronjs.org/docs/latest/api/notification).
У текущего неподписанного macOS-пакета доставка не гарантируется.

«Запускать вместе с системой» доступно только установленному приложению:
Windows/macOS — Login Item API Electron, Linux — пользовательский XDG autostart
файл `duprove.desktop`. Автозапуск открывает приложение, но не начинает и не
продолжает задание. Реальные вход в систему, доставка уведомлений и особенности
системного трея требуют отдельной проверки на целевых настольных средах.
