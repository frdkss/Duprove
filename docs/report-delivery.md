# Отправка отчётов — этап 8

Основание: требования `TODO.md`, решение пользователя о локальном Docker и код
`electron/services/delivery-service.ts`, `report-transport.ts`, Python-приёмника.
Публичное размещение остаётся отложенным. Параметры повторов ниже выбраны при
реализации этапа 8; это не ранее согласованные параметры внешнего хостинга.

## Когда отправляется отчёт

Main создаёт один `DeliveryService` с тем же `ConsentService`, который обслуживает
переключатель настроек. Сервис читает подготовленные отчёты при запуске приложения
и после завершения/остановки анализа. Исходные оболочки `{version, consentGrantId,
report}` не переписываются и не получают новую метку согласия. Частичные валидные
отчёты допускаются; `complete=false` сохраняется в теле.

Каждая попытка заново читает исходный файл, проверяет схему и арифметику. Затем
`sendReport` непосредственно перед транспортом проверяет текущее разрешение,
совпадение `grantId` и сигнал отмены. При отказе или несовпадении периода отчёт
исключается из отправки и остаётся локально. Повторное включение не разрешает
старые отчёты. Отзыв отменяет активный запрос; уже принятые сервером данные
отозвать таким способом нельзя.

Чтение файлов асинхронное; за раз загружается один отчёт, с пределом 2 МиБ + 4 КиБ
для локальной оболочки. Тело HTTP дополнительно ограничено 2 МиБ. Проверка JSON
выполняется в локальном сервисе main; большие непригодные для сервера отчёты
отклоняются до полного чтения. Состояния доставки читаются с пределом 4 КиБ.
Пути, рабочая БД и результат проверки содержимого транспорт не получает.

## Повторы и сохранение

- Одна передача одновременно, не чаще раза в 12 секунд для всего профиля.
- До 5 попыток на отчёт: первая сразу, следующие не ранее чем через 1 минуту,
  5 минут, 30 минут и 6 часов после предыдущей попытки. `Retry-After` может
  увеличить задержку до 24 часов. Общее окно — 24 часа от первой попытки.
- Сетевые/TLS-ошибки, обрывы, неверные подтверждения и HTTP 408/429/500/502/503/504
  допускают ограниченный повтор. Остальные HTTP-ошибки, в том числе 409/413/422
  и редиректы, завершают автоматическую отправку данного отчёта с ошибкой.
- Случайный UUID отчёта, число попыток, первая попытка, следующий срок и статус
  сохраняются **до** обращения к сети в `userData/analysis/delivery/<отпечаток>.json`.
  Отпечаток связывает состояние с именем локальной записи и байтами оболочки;
  этот SHA-256 и локальная метка согласия не передаются серверу.
- После перезапуска сохраняются ID, задержка и лимит попыток. Неподтверждённая
  передача повторяется с тем же ID. Повреждённое состояние запрещает отправку;
  ошибка его сохранения не позволяет начать новый сетевой запрос.
- При выходе приложения активный запрос отменяется. Повторы выполняются только
  пока приложение запущено; отдельный процесс после закрытия не остаётся.

Сроки используют системные часы. Проверки ускоряют время искусственными часами;
сутки реального ожидания не измерялись. Ручное удаление/подмена служебных данных
вне приложения не входит в гарантии восстановления.

## HTTPS и подтверждение

`POST /v1/reports`: только JSON контракта v1, `Content-Type`, `Content-Length`,
`Idempotency-Key` (случайный UUID конкретного отчёта), обычные `Host` и `Connection`.
Нет cookies, User-Agent с идентификатором, путей, метки согласия или диагностических
параметров URL. Перенаправления не выполняются. Проверка сертификата обязательна,
минимальная версия TLS — 1.2. Абсолютный тайм-аут 20 секунд включает DNS,
соединение, TLS, отправку и чтение ответа; размер ответа ограничен 4 КиБ.

Успех требует HTTP 200/201 и JSON ровно с `accepted=true` и `receipt_id`, равным
отправленному UUID. Сам HTTP 201, чужая квитанция или оборванный ответ успехом
не считаются. Тексты сетевых исключений/ответов сервера не журналируются и
не передаются UI; используются фиксированные коды.

Python проверяет UUID и в одной транзакции ищет запись по нему. Повтор того же
валидного канонического JSON возвращает прежний `receipt_id` с 201, не увеличивает
квоту и не продлевает срок хранения. Другой JSON под тем же UUID получает 409.
Проверка повторов работает при конкурентных запросах и после перезапуска сервера.
Это номер отчёта, а не постоянный номер пользователя или устройства. Схема JSON v1
не менялась; старые запросы без заголовка по-прежнему получают новый серверный UUID
и не имеют защиты от повторного учёта.

Защита действует пока запись хранится на сервере (30 дней по текущей политике).
Клиент ограничивает повтор 24 часами от первой попытки. Удаление серверной БД
также удаляет сведения о принятых UUID; после такого удаления гарантий нет.
Резервирование идентификатора отдельным запросом и постоянные пользовательские
идентификаторы не используются.

## Конфигурация и интерфейс

Для локальной разработки сначала `npm run server:dev`, затем обычный запуск
приложения. Непакетированное приложение читает `DUPROVE_REPORT_URL` и
`DUPROVE_CA_FILE` из корневого `.env` (переменные процесса имеют приоритет).
Самоподписанный тестовый CA разрешён только для loopback; он не добавляется
в доверие ОС. IP Docker служит диагностике; запрос идёт по опубликованному
`https://127.0.0.1:8443/v1/reports`. После изменения настройки сервера приложение
нужно перезапустить.

Установленная программа не читает `.env` из текущего каталога и не принимает
путь тестового CA. Публичного адреса по умолчанию нет. Пока он не определён,
пакет без явно настроенного `DUPROVE_REPORT_URL` сохраняет отчёты локально.
HTTPS URL с логином/паролем, query string, fragment или иным путём отклоняется.
Ошибочная/отсутствующая конфигурация не блокирует анализ.

`getReportDelivery()` и `onReportDelivery()` через ограниченный IPC возвращают
только счётчики доставки, состояние настройки, срок следующей попытки и фиксированный
код ошибки. Адрес сервера, сертификат, UUID отчёта, grantId и пути через это API
не выдаются. Компонент `ReportDelivery` показывает доставленные, ожидающие,
исключённые и не доставленные отчёты отдельно от результата анализа, в обзоре
и настройках. Перезагрузка/размонтирование UI не запускает отправку повторно.

## Проверки

`npm test` включает очередь, согласие, восстановление, исчерпание попыток,
ошибки записи и конфигурации. `npm run test:server` проверяет атомарную дедупликацию.
`npm run test:delivery:deployment` требует собранный анализатор, Node, Python,
Docker Compose и openssl (либо `--tls-dir` с тестовым localhost-сертификатом).
Он создаёт отдельный случайный Compose-проект, проверяет HTTPS-транспорт и путь
от анализа искусственных файлов до приёмника, повтор после неподтверждённого
ответа и перезапуска клиента, затем удаляет свои контейнеры, сети и том.

Состав настоящего HTTP-запроса проверяется тестовым HTTPS-сервером. Сквозной тест
ищет синтетические имена/пути/содержимое и локальную метку в передаваемом JSON.
Это проверка полей и искусственных данных, не доказательство отсутствия
пользовательского текста в произвольном расширении; ограничение контракта
описано в [statistics.md](statistics.md). Результаты и платформенные ограничения:
[verification.md](verification.md).
