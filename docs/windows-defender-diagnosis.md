# Диагностика Defender и подписей Windows — 2026-10-20

Основание: исходники и конфигурация текущей рабочей копии, фактические локальные
сборки и сканирования, `Get-AuthenticodeSignature`, документация Microsoft.
Production-код, исходный анализатор и установщик в этой проверке не изменялись.

## Повторная проверка перед выпуском

Дополнительное сканирование 2026-10-19 в 23:09 UTC (20 октября, 02:09 МСК),
Engine `1.1.26090.9`, базы `1.461.110.0`: установщик — clean;
`build/native/bin/duprove-analyzer.exe` — clean; анализатор в
`release/windows-installer/win-unpacked/resources/analyzer` —
`Trojan:Win64/Tedy.PGL!MTB`.
У обоих анализаторов один SHA-256:
`d41a46eca99d06fac86eef2e253c6ec7ac57f289b7c17d0a0157d80000649eff`.
В этом сравнении байты файлов совпадают полностью, включая метаданные PE.
Почему Defender выдаёт разные результаты для этих экземпляров, неизвестно;
причина в конкретной функции исходного кода этим не установлена.

Отчёты: `.verification/defender/current-installer.json`,
`current-production-analyzer.json`, `current-packaged-analyzer.json`.
В `release/windows-installer/defender-report.json` выставлено
`releaseEligible: false`: чистого результата внешнего установщика недостаточно,
если анализатор в распакованном приложении обнаруживается.
Ниже сохранены результаты предыдущего полного диагностического запуска.

## Воспроизведение

```powershell
npm run diagnose:defender -- --update-signatures
# Повторить только сканирование уже собранных образцов:
npm run diagnose:defender -- --scan-only
```

Сборки изолированы в `.verification/defender-ladder/build`. Запуски сохраняются
отдельно в `.verification/defender-ladder/runs/<UTC-время>/`; `latest-run.txt`
указывает последний запуск. Возвращаемый код 1 означает наличие обнаружений,
код 2 — ошибки проверок, код 0 — все проведённые сканирования clean.

Диагностические EXE не запускаются. Символы удерживаются реальными ссылками;
линкерные MAP-файлы подтверждают попадание нужных объектных модулей. Импорт DLL
также сохраняется. Просто добавить `.lib` в команду линковки недостаточно:
неиспользуемый код может быть исключён. Это описано в
[документации MSVC об оптимизации линковки](https://learn.microsoft.com/en-us/cpp/build/reference/opt-optimizations?view=msvc-170).
Проверка не означает, что в каждом образце присутствует каждая функция библиотеки.

## Что удалось установить точнее

| Бинарник | SHA-256 | Defender |
| --- | --- | --- |
| Существующий production analyzer | `d41a46eca99d06fac86eef2e253c6ec7ac57f289b7c17d0a0157d80000649eff` | clean |
| Новый диагностический полный analyzer M | `f1f87860dcd6837d75bfad01f82bbea7b6623f7c9a8ee7d69b871e5ff65a4719` | blocked |

Оба файла имеют размер 2 446 848 байт. Побайтовое сравнение установило:

- `.text`, `.data`, `.pdata`, `.fptable`, `.rsrc`, `.reloc` совпадают;
- в `.rdata` отличаются только байты поля времени в debug directory;
- во всём файле различаются четыре байта: в COFF TimeDateStamp и времени debug directory;
- различий за пределами этих двух полей времени не обнаружено.

Это проверено на самих файлах, а не предположено по одинаковым исходникам.
Отчёт: `.verification/defender-ladder/pe-comparison.json`; его содержимое также
включено в JSON последнего запуска. Значение полей времени описано в
[спецификации PE Microsoft](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format).

Следовательно, разное обнаружение этой пары нельзя объяснить изменением машинного
кода scanner. Даже наличие `scan()` отдельно не оказалось достаточным условием:
O проходит проверку. Точное правило Defender неизвестно; изменение идентификатора
файла, репутационные/облачные сведения или другие сигналы — возможные объяснения,
а не установленные причины. Классификацию как ложную Microsoft пока не подтвердила.
Исходные файлы для сравнения не патчились и не заменялись.

## На каком шаге останавливалась обычная сборка

`npm run package` выполняет CMake, TypeScript/Vite и запускает electron-builder.
Его `beforePack` вызывает `scripts/verify-package.cjs`, который проверяет архитектуру
и вызывает Defender для `build/native/bin/duprove-analyzer.exe`. При обнаружении
`check-windows-defender.cjs` выбрасывает `WINDOWS_DEFENDER_CHECK_FAILED`.
Это происходит до создания NSIS-установщика, а не при работе scanner на диске.
Готовый установщик дополнительно проверяется после упаковки.

Положительный результат для существующего EXE относится к конкретному SHA-256;
он не доказывает, что другая пересборка пройдёт. NSIS, выбор папки и текст лицензии
не объясняют обнаружение отдельного нативного EXE до упаковки.

## Проблемы с цифровой подписью

Результат `Get-AuthenticodeSignature`:

| Файл | Статус | Издатель / timestamp certificate |
| --- | --- | --- |
| `build/native/bin/duprove-analyzer.exe` | NotSigned | нет |
| `release/windows-installer/win-unpacked/Duprove.exe` | NotSigned | нет |
| `release/windows-installer/Duprove-1.0.0-win-x64.exe` | NotSigned | нет |
| анализатор внутри win-unpacked | NotSigned | нет |

Проверка стандартных хранилищ `CurrentUser\My` и `LocalMachine\My` нашла ноль
сертификатов Code Signing. Проверенные переменные настройки подписи в окружении
также отсутствуют. Это не проверка внешнего токена или отдельного облачного аккаунта.
Доказательства: `.verification/defender-ladder/signatures.json` и
`signing-environment.json`.

В `package.json` установлено `win.signExecutable: false`. Поэтому electron-builder
преднамеренно пропускает подпись приложения, установщика и деинсталлятора.
В release workflow подписывается только `stable.json` ключом Ed25519. Это корректный
отдельный механизм проверки обновлений, но он не создаёт Windows Authenticode.

Есть дополнительный пробел: установленный electron-builder 26.15.3 подписывает
файлы корня приложения и специально перечисленных каталогов, включая
`resources/app.asar.unpacked`. Каталог `resources/analyzer` в этом обходе отсутствует.
Одного переключения `signExecutable` недостаточно для подписи нативного анализатора.
Для него нужен отдельный шаг или signing hook до упаковки. Это проверено по
`node_modules/app-builder-lib/out/winPackager.js`, а не предположено по названию опции.

Статья Microsoft о подписи относится к удостоверению издателя и репутации
распространяемого приложения. Бесплатное переподписание Microsoft относится к
Store/MSIX; наш NSIS EXE на GitHub автоматически не переподписывается.
[Варианты подписи Windows](https://learn.microsoft.com/ru-ru/windows/apps/package-and-deploy/code-signing-options).

У подписанного нового приложения тоже может быть предупреждение SmartScreen.
EV не обеспечивает мгновенное доверие; самоподписанный сертификат не даёт общего
доверия для публичного распространения.
[Репутация SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).
Отсутствие подписи не объясняет различие нашей пары: оба EXE не подписаны, но
результат обнаружения разный.

## Как исправлять

1. Для обнаружения Tedy подготовить обращение о предполагаемом ложном срабатывании
   в Microsoft: обнаруживаемый M/core-test, версии Defender, SHA-256, рецепт сборки
   и результат сравнения с clean-файлом. Нужен вердикт по конкретному образцу,
   а не переписывание scanner или изменение двоичных метаданных ради результата.
   [Microsoft принимает такие образцы](https://www.microsoft.com/en-us/wdsi/filesubmission).
   Черновик обращения — `.verification/defender-ladder/microsoft-submission.txt`;
   отправка не выполнялась.
2. Выбрать доверенную подпись для Windows. Для открытого GPL-проекта возможна
   заявка в SignPath Foundation; одобрение требует выполнения их условий.
   [Правила SignPath](https://signpath.org/terms) требуют, в частности, возможности
   отключить передачу пользовательских данных при установке. У нас уведомление
   есть, но отдельной опции отключения статистики в установщике нет; она находится
   в настройках приложения. При включённой отправке это условие нужно отдельно учесть.
   Там же осталась фраза «В текущей версии сетевой отправки ещё нет», хотя
   HTTPS-транспорт уже реализован. Уведомление установщика нужно согласовать с
   актуальным `docs/statistics-notice.txt`; это отдельная найденная неточность,
   а не установленная причина Tedy.
3. Альтернатива — Azure Artifact Signing либо сертификат доверенного УЦ. Доступность
   зависит от юридического статуса и страны. Для физических лиц Azure Public Trust
   в актуальной документации ограничен США и Канадой; для организаций перечень шире,
   чем в сводной статье. Регистрацию пользователя я не знаю.
   [Текущие условия Azure](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart).
4. После получения доступа к подписи убрать `signExecutable: false`, настроить
   поддерживаемый в установленной версии механизм (`signtoolOptions` либо
   `azureSignOptions`) и отдельную подпись анализатора. Использовать SHA-256 и
   доверенный timestamp. Включить `forceCodeSigning` и явную проверку Authenticode
   для собственных EXE; без настроенных ключей эти требования остановят выпуск.
   [SignTool и проверка подписи](https://learn.microsoft.com/en-us/dotnet/framework/tools/signtool-exe).
5. Соблюдать порядок: собрать анализатор → подписать его → упаковать и подписать
   приложение/деинсталлятор/установщик → проверить подписи и Defender на итоговых
   файлах → вычислить хеши и подписать метаданные обновления → публиковать.
   Изменение файла после подписи или после вычисления хеша нарушит соответствующую
   проверку целостности.

Этот аудит не меняет настройки Defender, его исключения, карантин или доверенные
корневые сертификаты Windows. Production-функции в этой работе не менялись.
