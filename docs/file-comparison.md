# Этап 4: проверка файлов

Основание: `TODO.md`, согласованные там правила и исходный код анализатора.
Реализованы четыре уровня в общем C++-ядре для Windows, Linux и macOS.
2026-10-14 пользователь согласовал TXT/Markdown, DOCX и PNG/JPEG с отдельными
предупреждениями `warn`. Численные пороги и правила нормализации ниже —
технические решения этой реализации, а не дословные требования пользователя.
Результаты фактических проверок перечислены в `verification.md`.

## Точные дубликаты

1. Обход сохраняет имя, размер, время изменения, время изменения метаданных
   и идентичность физического файла в локальную SQLite. Непустой файл становится
   кандидатом, если в выбранных корнях есть хотя бы ещё один файл того же размера.
   Имя и дата сортируют работу внутри размера, но не исключают переименованные
   копии или файлы с разными датами. Одинаковые имя, размер и дата не доказывают
   равенство байтов.
2. Только кандидаты хешируются SHA-256 блоками по 256 KiB. Память буфера не зависит
   от размера файла. Размер и хеш отбирают пары для следующего уровня.
3. Пары сравниваются блоками по 256 KiB на файл; первое различие прекращает чтение.
   Совпадение хеша само по себе не подтверждает дубликат. Внутри одного размера
   и хеша могут возникнуть разные группы байтов, в том числе при коллизии хеша.

Перед чтением и после него сверяются идентичность, размер, mtime и ctime.
Перед окончательным отчётом метаданные членов групп проверяются снова.
Ошибки открытия/чтения, изменение и исчезновение файла отличимы от корректно
прочитанных разных байтов. Недоступный кандидат исключается из группы, увеличивает
счётчик ошибок своего корня и приводит к `complete=false`. При недоступности
представителя проверяется следующий сохранившийся член группы. Остановка любого
из двух сравниваемых корней не подтверждает пару.

Анализ живой файловой системы не является атомарным снимком: изменение после
последней проверки возможно. Дополнительные правила ссылок, исключений и доступа
описаны в [безопасном обходе](safe-traversal.md).

## Группы и локальные данные

- Одинаковые байты объединяются между всеми выбранными корнями независимо
  от расширения. Группа из N файлов даёт N экземпляров и N − 1 лишних копий.
- Пустые файлы получают тип `empty` и отдельный счётчик; они не хешируются
  для поиска дубликатов и не входят в группы.
- Несколько жёстких ссылок учитываются один раз. Символические ссылки пропускаются.
- Расширения сравниваются без учёта ASCII-регистра; без расширения — `none`.
  Реализованный список составных расширений: `.tar.gz`, `.tar.bz2`, `.tar.xz`,
  `.tar.zst`. Остальные имена используют последнее расширение, а не все точки.
- Имена, даты, пути, идентичности и хеши остаются в рабочей SQLite. В `result.report`
  входят только агрегаты существующего контракта версии 1.
- Старая рабочая БД получает отсутствующие поля; инвентарь перестраивается.
  Переиспользование хешей и сохранение незавершённого задания относятся к этапу 5.

## Дополнительное содержание

В локальном задании `--job` параметр `"content": true` включает дополнительную
проверку; отсутствие параметра или `false` оставляет только точные дубликаты.
Проверяются все обнаруженные файлы поддерживаемых форматов, включая разные
размеры и разные расширения. Переключатель и запуск анализа из UI относятся
к следующим этапам; уровень 4 уже доступен независимому CLI/ядру.

### Текст

- `.txt`, `.md`, `.markdown`: строгий UTF-8 с BOM или без него, либо UTF-16 LE/BE
  с BOM. Ошибочные последовательности, NUL и управляющие символы, кроме
  пробельных, отклоняются. Кодировка Windows-1251 не угадывается.
- Markdown разбирается CommonMark: оформление, разметка заголовков и адрес ссылки
  исключаются; остаётся отображаемый текст, подпись ссылки и текст кода.
  Встроенный HTML и изображения дают `unsupported`, без частичного сравнения.
- DOCX читается в памяти как ZIP/OOXML. Учитываются текст тела, таблиц, колонтитулов,
  сносок и концевых сносок. Тело сохраняет порядок текста, вспомогательные части
  сортируются по извлечённому тексту, независимо от имён частей ZIP.
  Стиль, шрифт и форматирование не участвуют. Рисунки, формулы, объекты, поля,
  удалённый текст правок, альтернативное содержимое и скрытый текст с явным
  `vanish` дают `unsupported`, чтобы не выдавать совпадение частично прочитанного
  документа. Это проверка текстовых DOCX, а не рендеринг Word.
- Последовательности Unicode White_Space заменяются одним обычным пробелом;
  крайние пробелы удаляются. Регистр, пунктуация, порядок текста и Unicode
  нормальная форма не меняются. Пустой нормализованный текст не создаёт `warn`.
- SHA-256 нормализованного текста отбирает кандидатов; затем строки сравниваются
  полностью. Текст может совпасть между TXT, Markdown и DOCX.

ZIP проверяется на CRC, шифрование, повторные имена и недопустимые пути.
Архив не распаковывается на диск. XML не загружает внешние сущности или ресурсы;
DTD, неизвестные сущности, повреждённый XML и неверная структура отклоняются.
Пароли, макросы, внешние ссылки и команды не исполняются.

### Изображения

PNG и JPEG (`.png`, `.jpg`, `.jpeg`) декодируются в RGBA. PNG CRC и конец контейнера
проверяются; предупреждения JPEG-декодера считаются ошибкой. APNG и JPEG CMYK/YCCK
пропускаются как неподдерживаемые. Учитываются восемь EXIF-ориентаций; RGB
умножается на alpha, поэтому скрытый цвет полностью прозрачного пикселя не влияет.

Изображение уменьшается усреднением площади до 32×32 RGBA. Пара получает `warn`
только при выполнении всех условий:

- относительное различие пропорций не больше 1%;
- расстояние Хэмминга между 64-битными dHash не больше 10;
- среднее абсолютное различие нормализованных каналов не больше 0,035;
- среднеквадратичное различие не больше 0,06, максимальное — не больше 0,30.

Это эвристика для одинакового изображения после масштабирования/сжатия,
а не доказательство равенства. Возможны пропуски и ложные предупреждения:
в частности, небольшие правки могут оставаться в пределах порогов. ICC/gamma
цветоуправление, распознавание объектов и поиск совпадений после обрезки не входят
в эту политику. Качество не заявляется для всех изображений по одним контрольным
примерам. Точные дубликаты по-прежнему требуют одинаковых байтов.

### Результат и ограничения

`result.content` — отдельный локальный контракт с `policy_version=1`, флагами
`enabled`/`complete`, счётчиками статусов файлов, числом пар по типу и массивом
`warnings`. Каждая запись имеет `status="warn"`, `kind="text"|"image"` и ровно
два локальных идентификатора файлов с номером корня, расширением и категорией.
Идентификаторы действуют только для текущей рабочей БД. Имён, путей, текстов,
пикселей и хешей в этом результате нет.

Предупреждения считаются парами: сходство не транзитивно, поэтому A–B и B–C
не создают автоматически A–C. Точная пара никогда не дублируется как `warn`.
Число предупреждений не является количеством лишних копий. `result.report`
остаётся статистическим контрактом v1 только о точных совпадениях. Отправитель
получает только этот отчёт; `contentFromEvent()` отдельно валидирует локальный
результат, а схема отчёта запрещает добавлять к нему `content`.

Статусы файлов: `ready`, `empty` (в том числе пустой нормализованный текст),
`unsupported`, `invalid`, `protected`, `limit`, `unavailable`, `stopped`.
`protected` означает ZIP с флагом шифрования либо OLE-контейнер Office, который
этот анализатор не расшифровывает и не разбирает. Наличие конкретного пароля
у OLE-контейнера не устанавливается. Пропуск формата/повреждённого контейнера
показывается счётчиком и не создаёт совпадения. `complete` означает завершение
прохода с перечисленными пропусками; ошибки доступа, изменение файлов и остановка
дают частичный результат.

Пределы: текстовый вход и отдельная XML-часть — 8 MiB; DOCX/изображение на диске —
64 MiB; все распакованные данные ZIP — 64 MiB, не больше 4096 записей;
изображение — 16 777 216 пикселей. Раздувание PNG ограничено до выделения
неограниченного выходного буфера. JPEG ограничивает память декодера и число
прогрессивных проходов. Превышение входного предела даёт `limit`; ошибка внутри
декодера может дать `invalid`. Это пределы файлов/буферов, а не обещание общего
фиксированного RSS: DOM, индексы и итоговый список пар требуют дополнительной
памяти. Масштабирование результата и лимиты режимов нагрузки — этап 5.

Нормализованные строки и пиксели живут только в памяти. Рабочая SQLite хранит
метаданные, внутренние хеши и связи пар. Повторная проверка метаданных удаляет
предупреждения изменившихся/исчезнувших файлов; остановленный корень также
теряет пары. Следующий анализ перестраивает содержимое этих таблиц, а запуск
с `content=false` очищает предыдущие предупреждения.

### Зависимости

Парсеры статически связываются с анализатором и не требуют Python, Word,
браузера, внешнего процесса или сети при анализе. CMake фиксирует commit и SHA-256
архива. Лицензии копируются в пакет приложения из `build/native/licenses`.

- [cmark 0.31.1](https://github.com/commonmark/cmark/tree/bb3678d7a73cb02d35c8876ecd097072636200a8) — CommonMark.
- [miniz 3.1.0](https://github.com/richgel999/miniz/tree/174573d60290f447c13a2b1b3405de2b96e27d6c) — ZIP.
- [pugixml 1.15](https://github.com/zeux/pugixml/tree/ee86beb30e4973f5feffe3ce63bfa4fbadf72f38) — XML.
- [LodePNG](https://github.com/lvandeve/lodepng/tree/e584a8490db1b76b81bf298c11c09d3b55d9c270) — PNG.
- [libjpeg-turbo 3.1.2](https://github.com/libjpeg-turbo/libjpeg-turbo/tree/4e151a4ad91001b3aa8c2ece2205c15f487ce320) — JPEG; отдельная статическая сборка через ExternalProject, без обязательного NASM.

## Проверка

```text
cmake --build build/native --config Release
ctest --test-dir build/native -C Release --output-on-failure
npm run test:comparison
npm run test:content
```

`exact-comparison` проверяет известные SHA-256 векторы, размеры на границах блоков,
различия байтов, остановку каждого корня, устаревшие метаданные и исчезновение.
В отдельном сценарии искусственно одинаковые хеши подаются в реальную функцию
группировки: разные байты остаются в разных группах. Это симуляция коллизии,
а не найденная коллизия SHA-256. Проверяется подмена файла между хешированием
и сравнением с восстановлением mtime.

`tests/test_comparison.py` запускает настоящий CLI на временных искусственных
файлах: переименованные копии, разные даты, несколько корней, одинаковые метаданные
при разных байтах, большие файлы, расширения, пустые файлы, жёсткие ссылки,
отсутствие частных данных в отчёте и миграция рабочей БД.
CI настроен на эти проверки на Windows, Linux, macOS Intel и Apple Silicon.
Фактические локальные результаты и ограничения записываются в
[журнале проверки](verification.md).

`content-comparison` и `test_content.py` проверяют форматы, нормализацию,
масштабирование/сжатие, EXIF, alpha, повреждения, шифрование, пределы, изменения
файлов и раздельный подсчёт. Все контрольные данные искусственные.
