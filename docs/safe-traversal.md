# Этап 3: безопасный обход и производительность

Основание: `TODO.md`, исходный код и локальные проверки 2026-10-14.
Обход и сравнение выполняются в C++ без зависимости от UI или сервера.

## Охват

- Windows: смонтированные фиксированные, съёмные и сетевые тома, включая тома
  без буквы, подключённые к каталогу. Виртуальный диск, представленный ОС обычным
  фиксированным томом, включается. Оптические носители, RAM-диски и неизвестные
  типы Windows не предлагаются.
- Linux: корневой том и пользовательские файловые системы, перечисленные
  в [политике обнаружения](drive-discovery.md). Системные виртуальные FS исключаются.
- macOS: видимые смонтированные тома из `getmntinfo`. Нативная сборка, Foundation,
  обход и временный APFS-том проверены в CI на Intel и Apple Silicon; см.
  [результаты](verification.md).
- Несмонтированные, заблокированные и недоступные тома не предлагаются.
  Программа не монтирует устройства и не повышает права. Недоступность уже
  выбранного корня даёт ошибку этого корня; остальные корни продолжают работу.
- Недоступная сеть может задержать системный вызов. Гарантированного тайм-аута
  каждого файлового запроса пока нет. Это относится и к паузе внутри такого вызова.

В UI уже есть галочки выбора. Внутренний `--job` принимает только явно переданные
абсолютные `roots`; повторы и `..` отклоняются. Вложенный выбранный корень
обрабатывается отдельно. Все точки монтирования, включая скрытые, виртуальные
и bind-mount, являются границами обхода: выбор родительского тома не выбирает их.
Указанные отдельно корни участвуют в общем сравнении. Кнопка запуска UI остаётся
задачей этапа 5 — управление заданиями и сохранение прогресса здесь не реализованы.

Снимок монтирований берётся в начале обхода; идентификатор устройства и каталога
проверяется при открытии. APFS Data включается в логический системный диск macOS,
поскольку пользовательские каталоги доступны через firmlinks. Изменение топологии
монтирований во время работы, особенно новый bind-mount той же FS, не является
атомарно защищённым сценарием; требуется повторный анализ после такого изменения.

## Исключения, ссылки и чтение

Системные пути отсекаются до перечисления содержимого. Windows исключает каталог
ОС, корневые `Program Files`, `Program Files (x86)`, `ProgramData`, `Recovery`,
`$Windows.~BT`, файлы подкачки и гибернации. Linux/macOS исключают служебные
деревья `/proc`, `/sys`, `/dev`, `/run` (кроме выбранных томов `/run/media`),
`/boot`, `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc`, `/var`, `/System`,
`/Library`, `/private`, `/snap`; macOS дополнительно `/Applications`.
На всех платформах исключаются `.git`, `.pytest_cache`, `$RECYCLE.BIN`, `System Volume Information`
и весь собственный рабочий каталог задания. Это фиксированная консервативная
политика этапа 3; пользовательское редактирование исключений пока не подключено.

Символические ссылки, Windows junction/reparse points и специальные файлы
(FIFO, сокеты, устройства) не читаются. Исключение — явно выбранная настоящая
Windows volume mount point. Идентичность каталогов хранится в уникальном индексе
очереди: повторные пути и циклы не увеличивают работу. Жёсткие ссылки считаются
одним файлом на весь набор корней; первый обработанный выбранный корень владеет
его записью. Это не выбор «оригинала» для удаления.

`Directory` открывает компоненты пути без перехода по symlink. На Windows
открытые каталоги удерживаются без `FILE_SHARE_DELETE`, ограничивая подмену пути;
на POSIX используются `openat`, `O_NOFOLLOW`, `fstatat`, `fdopendir`.
При переходе к следующему каталогу в Windows общие родители переиспользуются
через совместное владение открытыми дескрипторами. Пока новый каталог жив,
общая цепочка остаётся защищённой от переименования, даже если предыдущий
объект уже закрыт. Идентичность самого обрабатываемого каталога по-прежнему
сверяется с записью очереди; на POSIX это переиспользование не применяется.
Win32-вызовы получают расширенные абсолютные пути `\\?\…` и `\\?\UNC\…`:
это позволяет обходить и читать длинные пути без зависимости от настройки
`LongPathsEnabled` и манифеста запускающего процесса. В индексе и правилах
исключений остаются обычные пути. Основание:
[Microsoft — ограничения длины пути](https://learn.microsoft.com/windows/win32/fileio/maximum-file-path-limitation).
Файлы открываются исключительно для чтения; чтение POSIX специального файла
не может заблокироваться на FIFO. Для сравнения проверяются идентификатор,
размер, время изменения и время изменения метаданных до и после чтения.
Изменившиеся/исчезнувшие кандидаты теряют совпадения; подтверждённые группы
повторно проверяются перед отчётом. Хеши старого запуска пока не переиспользуются:
валидируемое возобновление и кэш — этап 5.

Это последовательный анализ живой FS, а не атомарный snapshot. Изменение после
последней проверки возможно. Счётчики файлов описывают обнаруженный набор
метаданных, включая файлы, содержимое которых позже оказалось недоступным.
Ошибки увеличивают локальный счётчик, дают `phase=error` и `report.complete=false`;
они не превращаются в успешный пустой результат. Полный набор файлов не читается
ради подсчёта: содержимое требуется только кандидатам по размеру.
ОС может обновить время последнего доступа; программа не изменяет содержимое,
mtime, имена и расположение пользовательских файлов.

## Категории

Windows использует `SHGetKnownFolderPath`; Linux —
`$XDG_CONFIG_HOME/user-dirs.dirs` (по умолчанию `$HOME/.config/user-dirs.dirs`);
macOS — `NSFileManager.URLsForDirectory` для пользовательского домена.
Linux-конфигурация разбирается как данные, без shell и исполнения подстановок.
Учитываются локализованные/перенесённые пути, экранирование, отключённые папки,
указанные как `$HOME`, и более вложенные стандартные категории.
При отсутствии сведений ОС имена каталогов не угадываются. Всё остальное
получает `custom` («Пользовательские папки»), без имён и структуры в статистике.
Список стандартных папок загружается один раз на задание; категория вычисляется
один раз на каталог.

Рабочая SQLite содержит пути и внутренние метаданные. `result.report` содержит
только разрешённые агрегаты. Локальные события `progress.disks`/`result.disks`
по-прежнему содержат пути корней и не предназначены для журналов или отправки.

## Оптимизация и замер

- Один запрос метаданных объекта вместо раздельных filesystem-запросов размера,
  даты и идентичности; Windows дополнительно получает ChangeTime из того же handle.
- Подготовленные SQL-запросы переиспользуются; транзакция обхода фиксируется
  каждые 1024 записи. Ошибка SQLite прерывает задание, а не скрывается как ошибка файла.
- Очередь каталогов на диске с индексом `(root, done, id)`, уникальные индексы
  физических объектов, SQLite page cache 4 MiB и `temp_store=FILE`.
- Размеры кандидатов вычисляются один раз на весь набор дисков. Составной индекс
  `(hash, size, gid)` исключает повторную сортировку растущих групп совпадений.
- Чтение последовательно блоками 256 KiB; одинаковые данные сравниваются с
  представителем группы, сравнение прекращается на первом отличии.

Это ограничения буферов обхода, не гарантия фиксированной памяти всего процесса:
итоговый JSON по-прежнему собирается в памяти, его масштабирование относится
к следующим этапам. Параллелизм и измеримые лимиты режимов нагрузки — этап 5.

Воспроизводимая команда:

```text
python tests/benchmark_traversal.py --binary build/native/bin/duprove-analyzer.exe
```

Windows, Release, 20 000 искусственных пустых файлов, 200 каталогов, режим `load=2`,
свежая БД в каждом запуске, прогретый файловый кэш. Измеряется весь CLI-запуск
после создания набора, включая обход и отчёт; содержимое не хешируется.

| Версия | Три запуска, с | Медиана, с | Файлов/с |
| --- | --- | --- | --- |
| До изменений | 5,532; 5,803; 5,646 | 5,646 | 3 542 |
| После изменений | 2,230; 2,278; 2,291 | 2,278 | 8 780 |

На этом сценарии ускорение около **2,48 раза**. Оно не переносится автоматически
на HDD, сеть, холодный кэш и хеширование больших файлов. Замер после изменений
совпал с работой Linux-сборки в WSL; это дополнительный источник разброса.
Результаты сохранены локально в `.verification/stage3-before.json` и
`.verification/stage3-after.json`. Максимальная скорость для всех устройств
не заявляется без соответствующих измерений.

## Источники API

- [Microsoft: CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea)
  — режимы открытия, reparse points и совместный доступ.
- [Microsoft: GetVolumePathNamesForVolumeNameW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamesforvolumenamew)
  — буквы и каталоги подключения томов.
- [Linux: open/openat](https://man7.org/linux/man-pages/man2/open.2.html)
  — открытие относительно дескриптора, `O_NOFOLLOW`, `O_NONBLOCK`.
- [freedesktop: xdg-user-dirs](https://wiki.freedesktop.org/www/Software/xdg-user-dirs/)
  — расположение конфигурации пользовательских папок.
- [Apple: использование файловой системы](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively?language=objc)
  — получение стандартных пользовательских каталогов через Foundation.
