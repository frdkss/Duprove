# Отчёт о правах администратора и доступе к файлам в DuProve

Дата проверки: 20 октября 2026 года.

Объект: исходники и конфигурация в рабочем каталоге `F:\pyproj\Duprove`.
Базовый Git-коммит: `333659199aa30b059f8228e770eaf9429c19cb94`.
В рабочем дереве на момент проверки есть незакоммиченные изменения. Выводы относятся к прочитанному состоянию файлов, а не только к этому коммиту.

## 1. Основной вывод

Текущий механизм сканирования DuProve не требует прав администратора для анализа файлов, к которым у запустившего программу пользователя есть необходимые разрешения.

Программа обходит каталоги через обычные Win32 API, получает метаданные файлов и читает их содержимое. Прямое чтение MFT, секторов физического диска или сырого тома в проверенных собственных исходниках не обнаружено.

Отсутствие запроса UAC согласуется с этим механизмом. Оно не означает, что программа получает доступ ко всем данным диска. Недоступные объекты приводят к диагностическим ошибкам, а наличие ошибок делает итоговый отчёт неполным.

Установщик Windows настроен без обязательной установки для всех пользователей и без запроса повышения прав. При установке в доступную пользователю папку административные права по этой конфигурации не нужны. Это не гарантирует возможность установки в произвольный защищённый каталог.

## 2. Основания и границы проверки

Использованы:

- Приложенный пользователем файл `Вставленный текст.txt`: исходный перечень вопросов о MFT, NTFS, привилегиях и Defender.
- Собственные исходники нативного анализатора, Electron-части, установщика и обновления.
- Конфигурация `package.json` и `native/CMakeLists.txt`.
- Исходник теста Windows с временным VHDX и отдельные тесты обработки недоступных объектов.
- Документация Microsoft о `CreateFileW` и UAC; локальная схема и шаблоны установленного `app-builder-lib` для уточнения настроек NSIS.

Метод: статический анализ, поиск вызовов API и чтение соответствующих ветвей выполнения.

В рамках этой проверки не выполнялись:

- Запуск DuProve под отдельной стандартной учётной записью и сравнение с повышенным запуском.
- Трассировка Process Monitor и проверка фактического токена процессов.
- Проверка PE-манифеста, импортов, подписи и SHA-256 конкретного EXE.
- Новая сборка и запуск тестов. Наличие теста в репозитории не считается его успешным выполнением в этой проверке.
- Полный аудит сторонних библиотек, Electron/Node.js и сгенерированных бинарных файлов.
- Полный аудит сети, антивирусного обнаружения, установщика и безопасности приложения в целом.

Поэтому формулировка «не обнаружено» относится к изученному коду и поиску по указанным каталогам. Она не является доказательством поведения любого EXE с названием DuProve.

## 3. Проверка исходного утверждения о NTFS/MFT

В приложенном тексте сказано, что программа напрямую обращается к NTFS/MFT/raw volume. Для текущих исходников это утверждение не подтверждается.

Нужно различать:

| Механизм | Что делает приложение | Обнаружено в текущем коде |
| --- | --- | --- |
| Обычный доступ к файлам на NTFS | Запрашивает у Windows каталоги, атрибуты и байты файлов | Да |
| Получение идентификатора файла | Читает сведения о файле через его дескриптор | Да |
| Перечисление записей MFT через USN API | Вызывает соответствующие управляющие операции файловой системы | Не обнаружено |
| Чтение USN Journal | Читает журнал изменений тома | Не обнаружено |
| Сырое чтение тома или физического диска | Открывает устройство и читает его сектора | Не обнаружено |
| Собственный разбор бинарных записей MFT | Интерпретирует структуру MFT в приложении | Не обнаружено |

То, что Windows обслуживает запросы к файлам на NTFS с использованием собственных структур файловой системы, не означает, что DuProve самостоятельно читает или разбирает MFT.

## 4. Как выполняется сканирование

### 4.1. Обнаружение накопителей и точек монтирования

В [native/src/platform.cpp](native/src/platform.cpp) функции `mountPaths()` и `drives()` используют:

- `FindFirstVolumeW`, `FindNextVolumeW`, `FindVolumeClose`;
- `GetVolumePathNamesForVolumeNameW`;
- `GetLogicalDriveStringsW`;
- `GetDriveTypeW`;
- `std::filesystem::is_directory` и `std::filesystem::space`.

Это обнаружение томов, путей и доступного пространства. В просмотренной реализации нет открытия физического устройства для чтения секторов.

Само наличие слова `Volume` в названии API не доказывает использование сырого доступа. Важно, что именно возвращает функция и как результат применяется дальше.

### 4.2. Обход каталогов

В [native/src/file_access.cpp](native/src/file_access.cpp), функция `Directory::next()`:

1. Формирует путь каталога с маской `*`.
2. Запускает перечисление через `FindFirstFileExW`.
3. Продолжает через `FindNextFileW`.
4. Пропускает `.` и `..`, применяет исключения и проверяет метаданные.

Перечисление выполняется через файловую систему Windows. Отдельного основного пути через MFT и резервного пути при отказе сырого доступа в этом коде не найдено: обычный обход является основным механизмом.

### 4.3. Открытие каталогов и получение метаданных

Для каталогов и проверки записей используется `CreateFileW` со следующими параметрами:

| Параметр | Значение и назначение |
| --- | --- |
| Доступ | `FILE_READ_ATTRIBUTES`: получение атрибутов |
| Создание | `OPEN_EXISTING`: открытие существующего объекта |
| Флаги | `FILE_FLAG_BACKUP_SEMANTICS` для открытия каталога; в обычной ветви также `FILE_FLAG_OPEN_REPARSE_POINT` |
| Совместный доступ | `FILE_SHARE_READ | FILE_SHARE_WRITE`; при проверке отдельной записи также `FILE_SHARE_DELETE` |

Метаданные получает функция `metadata(HANDLE)` через `GetFileInformationByHandle` и `GetFileInformationByHandleEx`.

Из результата берутся тип, размер, времена изменения, серийный номер тома и индекс файла. Идентификатор строится из серийного номера тома и частей индекса. Это получение сведений через Windows, а не самостоятельный разбор MFT.

`FILE_SHARE_WRITE` разрешает совместимые открытия другими процессами. Он не предоставляет текущему дескриптору право записи: запрашиваемые права задаёт отдельный аргумент `dwDesiredAccess`.

### 4.4. Чтение содержимого

`FileReader::FileReader()` открывает файл следующим образом:

```cpp
CreateFileW(systemPath.c_str(), GENERIC_READ,
    FILE_SHARE_READ | FILE_SHARE_WRITE,
    nullptr, OPEN_EXISTING,
    FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_SEQUENTIAL_SCAN,
    nullptr);
```

Затем проверяется `GetFileType`, а метаданные должны соответствовать обычному файлу. `FileReader::read()` читает байты через `ReadFile`.

Проверенный путь чтения содержимого запрашивает `GENERIC_READ`, не `GENERIC_WRITE`. Файл не создаётся и не усекается этим вызовом.

Этот вывод относится к исследуемым файлам. У приложения есть отдельные операции записи рабочих данных и обновления собственных файлов; утверждение «программа вообще ничего не записывает» было бы неверным.

## 5. Что означает FILE_FLAG_BACKUP_SEMANTICS

Название флага может создать впечатление, что приложение использует специальные права резервного копирования. Само наличие флага этого не доказывает.

Microsoft указывает, что он нужен для получения дескриптора каталога. Без соответствующих привилегий обычные проверки безопасности продолжают действовать. Источник: [CreateFileW — Directories и описание FILE_FLAG_BACKUP_SEMANTICS](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

В собственных проверенных исходниках не обнаружено включения `SeBackupPrivilege` или `SeRestorePrivilege`, а также вызовов `AdjustTokenPrivileges`.

Следовательно, по изученному коду нет основания считать этот флаг механизмом повышения прав или обхода разрешений.

## 6. Длинные пути, ссылки и точки монтирования

`nativePath()` добавляет префикс расширенных путей `\\?\` и формирует `\\?\UNC\` для сетевых путей. Назначение видно из комментария и преобразования: поддержка длинных имён на границе Win32.

Такой префикс в этом коде не является свидетельством открытия `\\.\PhysicalDrive0` или `\\.\C:` для сырого чтения.

Для обычных проверок используется `FILE_FLAG_OPEN_REPARSE_POINT`, а метаданные с признаком reparse point первоначально получают тип `skip`. При обходе записи с таким признаком фильтруются.

Есть отдельная ветвь открытия пути, если `GetVolumeNameForVolumeMountPointW` подтверждает точку монтирования тома. В этой ветви каталог повторно открывается без `FILE_FLAG_OPEN_REPARSE_POINT`. Это позволяет работать с каталогом подключённого тома; чтения секторов через эту ветвь нет.

В [native/src/traversal.cpp](native/src/traversal.cpp) также учитываются границы томов и выбранных корней. Наличие повышенных прав само по себе не отменяет эти правила обхода.

## 7. Что происходит при отказе доступа

В [native/src/traversal.cpp](native/src/traversal.cpp) обнаружены следующие ветви:

| Ситуация | Код диагностики | Поведение |
| --- | --- | --- |
| Не удаётся открыть выбранный корень | `root_unavailable` | Корень получает фазу `error`, обрабатываются следующие корни |
| Не удаётся открыть очередной каталог | `directory_unavailable` | Каталог не обходится, анализ продолжается |
| Ошибка перечисления каталога | `enumeration_failed` | Перечисление этого каталога прекращается |
| Не удаётся прочитать метаданные записи | `metadata_unavailable` | Запись не добавляется как успешно проверенная |
| Файл недоступен или изменился при проверке | `file_unavailable_or_changed` | Запись инвалидируется в соответствующей ветви анализатора |

Последняя ветвь находится в [native/src/scanner.cpp](native/src/scanner.cpp); обработка недоступных файлов при сравнении — в [native/src/comparison.cpp](native/src/comparison.cpp).

В финализации `scanner.cpp` любой ненулевой счётчик `errors` приводит к фазе диска `error` и `complete = false`. Таким образом, продолжение доступной части анализа не означает успешную полную проверку всего диска.

Ограничение диагностики: низкоуровневая функция `failed()` в `file_access.cpp` выбрасывает общий `FILE_ACCESS_FAILED`. По перечисленным кодам нельзя достоверно отличить отказ ACL от удаления файла, блокировки или некоторых других ошибок. Поэтому каждый `directory_unavailable` нельзя автоматически объяснять отсутствием административных прав.

## 8. Намеренные исключения

Функция `excluded()` в [native/src/platform.cpp](native/src/platform.cpp) исключает, в частности:

- `.git`, `.pytest_cache`, `$Recycle.Bin`, `System Volume Information`;
- каталог Windows;
- корневые каталоги `Program Files`, `Program Files (x86)`, `ProgramData`, `Recovery`, `$Windows.~BT`;
- `pagefile.sys`, `hiberfil.sys`, `swapfile.sys`.

Рабочий каталог анализа также отделяется от исследуемого дерева в `traversal.cpp`.

Это правила программы, а не обязательно отказы Windows. Повышение прав не делает такие области автоматически включёнными в сканирование. Даже `complete = true` нужно понимать в пределах правил обхода и исключений, а не как обещание прочитать каждый объект диска.

## 9. Запуск анализатора, установка и обновление

### 9.1. Запуск анализатора

В [electron/services/analyzer-service.ts](electron/services/analyzer-service.ts) список накопителей получается запуском EXE с `--drives` через `execFile`.

В [electron/services/job-service.ts](electron/services/job-service.ts) задание запускается через:

```ts
spawn(file, ['--job', input], {
  windowsHide: true,
  stdio: ['pipe', 'pipe', 'pipe']
})
```

В этих местах нет отдельного запроса повышения прав. `windowsHide` управляет видимостью окна запуска и не обозначает уровень привилегий.

Отсутствие запроса повышения не означает принудительного снижения прав. Если приложение уже запущено в повышенном контексте, рассмотренные вызовы не содержат отдельного механизма запуска анализатора с ограниченным токеном. Фактический токен конкретного процесса в этой проверке не измерялся.

### 9.2. Установщик Windows

В [package.json](package.json), секция `build.nsis`:

```json
{
  "oneClick": false,
  "perMachine": false,
  "allowElevation": false,
  "allowToChangeInstallationDirectory": true
}
```

`perMachine: false` не задаёт обязательную установку для всех пользователей. Для мастера `oneClick: false` этот параметр сам по себе не следует трактовать как абсолютный запрет любого режима установки для всех пользователей. `allowElevation: false` отключает запрос повышения со стороны мастера; он не предоставляет доступ к защищённым папкам.

Это уточнение основано также на локальной схеме `node_modules/app-builder-lib/scheme.json` и шаблонах NSIS. Справочная страница проекта: [electron-builder — NSIS](https://www.electron.build/nsis/).

В [installer/installer.nsh](installer/installer.nsh) маркер `.duprove-managed` записывается для режима `CurrentUser`. В просмотренном пользовательском дополнении к установщику нет установки драйвера или службы.

### 9.3. Обновление Windows

В [electron/services/update-installer.ts](electron/services/update-installer.ts) поддержка управляемого обновления проверяет маркер установки и доступность записи в каталог приложения и его родительский каталог.

В [installer/update-windows.ps1](installer/update-windows.ps1) установщик запускается с `/S`, `--updated`, `/currentuser` и целевым каталогом. В изученном сценарии нет `-Verb RunAs`.

Обновление записывает и заменяет файлы самого приложения, создаёт резервную копию и при ошибке выполняет восстановление. Это отдельная операция от чтения пользовательских файлов при сканировании. Отсутствие запроса администратора не означает отсутствие файловых изменений при обновлении.

### 9.4. Рабочие данные

В [electron/main.ts](electron/main.ts) каталог анализа формируется как `app.getPath('userData')/analysis`. `JobService` размещает базу в `work/index.sqlite` внутри переданного каталога.

В `scanner.cpp` проверяется расположение базы внутри `private_directory`; создаются рабочие каталоги, открывается SQLite, для временных данных установлен `PRAGMA temp_store=FILE`.

Следовательно, приложению нужны права записи в собственные рабочие каталоги и используемый временный каталог. Это отдельное требование от прав чтения исследуемых файлов. Точный абсолютный путь `userData` конкретного установленного экземпляра в этой проверке не измерялся.

## 10. Почему тест VHDX требует администратора

[tests/test_windows_volume_mount.ps1](tests/test_windows_volume_mount.ps1) явно проверяет административный контекст и выдаёт `WINDOWS_VOLUME_TEST_REQUIRES_ADMINISTRATOR`, если его нет.

Тест создаёт временный VHDX, подключает его, инициализирует диск, создаёт раздел, форматирует его в NTFS и назначает точку подключения. Для подготовки этой среды используются `diskpart`, `Mount-DiskImage`, `Initialize-Disk`, `New-Partition`, `Format-Volume` и `Add-PartitionAccessPath`.

Это требование подготовки тестового тома, а не доказательство необходимости администратора для обычного файлового анализа.

Дополнительное ограничение: запуск анализатора из уже повышенного тестового сценария сам по себе не подтверждает работу без повышения. Такой тест и проверка стандартного пользовательского токена решают разные задачи. Здесь тест не запускался.

## 11. Результаты поиска специальных механизмов

Поиск выполнен по собственному коду в `native`, `electron`, `backend`, `installer`, `scripts`, `tests`.

| Механизм или API | Результат в просмотренном коде |
| --- | --- |
| `DeviceIoControl`, `FSCTL_*`, `IOCTL_*` | Совпадений соответствующего поиска не получено |
| `PhysicalDrive` | Совпадений не получено |
| `NtCreateFile`, `NtReadFile` | Совпадений не получено |
| `AdjustTokenPrivileges`, `SeBackupPrivilege`, `SeRestorePrivilege` | Совпадений не получено |
| `requireAdministrator`, `highestAvailable`, `requestedExecutionLevel`, `requestExecutionLevel` | В собственных проверенных файлах совпадений не получено |
| `IsUserAnAdmin`, `CreateService`, `Start-Service`, `-Verb RunAs` | Совпадений соответствующего поиска не получено |
| `CreateFileW`, `ReadFile` | Обнаружены; параметры рассмотрены в разделах 4–6 |
| Проверка принадлежности к администраторам | Есть в тесте VHDX через `WindowsPrincipal.IsInRole` |

Поиск имён API не обнаруживает автоматически все возможные динамические вызовы и не заменяет проверку бинарного файла. Сгенерированные шаблонами манифесты также не обязаны присутствовать в собственных исходниках в готовом виде. Поэтому отсутствие строки `requireAdministrator` в проекте не считается проверкой манифеста собранного EXE.

Для воспроизведения основных поисков из корня проекта:

```powershell
rg -n -i 'CreateFileW|ReadFile|FindFirstFileExW|FindNextFileW|GetFileInformationByHandle' native
rg -n -i 'DeviceIoControl|FSCTL_|IOCTL_|PhysicalDrive|NtCreateFile|NtReadFile' native electron backend installer scripts tests
rg -n -i 'AdjustTokenPrivileges|SeBackupPrivilege|SeRestorePrivilege|requireAdministrator|highestAvailable|requestedExecutionLevel|requestExecutionLevel|IsUserAnAdmin|CreateService|Start-Service|Verb.*runas' native electron backend installer scripts tests
rg -n 'allowElevation|perMachine|oneClick|allowToChangeInstallationDirectory' package.json
```

При отсутствии совпадений `rg` возвращает код 1. Это нормальный результат поиска, а не доказательство ошибки приложения.

## 12. Когда административные права имеют значение

| Сценарий | Вывод |
| --- | --- |
| Чтение доступных пользователю документов | Повышение для рассмотренного механизма не требуется |
| Чтение чужих или защищённых каталогов | Результат зависит от разрешений и контекста; полнота безусловно не гарантируется |
| Установка в доступный каталог пользователя | Конфигурация допускает работу без запроса повышения |
| Установка в защищённый каталог | Настройки установщика не обходят ограничения Windows |
| Создание и форматирование тестового VHDX | Тест требует администратора |
| Прямой доступ к физическому диску или сырому тому | Microsoft указывает административные привилегии среди требований; текущий сканер такой механизм не использует |

Для прямого доступа источник: [CreateFileW — Physical Disks and Volumes](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew#physical-disks-and-volumes).

При стандартной конфигурации UAC принадлежность учётной записи к группе администраторов и запуск процесса с повышенным токеном — разные вещи. Член группы администраторов может запускать обычные приложения со стандартным токеном. Источник: [Microsoft — How User Account Control works](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works).

Отсутствие окна UAC само по себе не доказывает уровень токена: процесс мог быть запущен из уже повышенного контекста. В рассмотренном коде нет основания обещать, что ручной повышенный запуск обеспечит чтение всех объектов или отменит исключения программы.

## 13. Что установлено и что остаётся неизвестным

**Установлено по текущим исходникам:**

1. Основной механизм — перечисление каталогов, получение метаданных и чтение обычных файлов.
2. Прямое чтение MFT/raw volume и специальные вызовы повышения привилегий не обнаружены.
3. Проверенный путь открытия исследуемого содержимого запрашивает чтение.
4. Ошибки доступа учитываются; наличие ошибок влияет на полноту итогового отчёта.
5. Установщик настроен без автоматического запроса повышения; обновление ориентируется на управляемую пользовательскую установку.
6. Административное требование теста VHDX связано с подготовкой тома.

**Не установлено этой проверкой:**

1. Совпадает ли конкретный распространяемый EXE с этими исходниками.
2. Какой манифест и токен имеет конкретный запущенный экземпляр.
3. Какие фактические отказы доступа возникнут на компьютере пользователя.
4. Почему Defender обнаруживает конкретную сборку.
5. Есть ли нежелательные действия в стороннем или сгенерированном коде, не охваченном анализом.

Утверждение «скрытого повышения прав нет вообще» было бы шире полученных доказательств. Корректная формулировка: в проверенных собственных исходниках механизм запроса или обхода повышения прав не обнаружен; текущий алгоритм сканирования не нуждается в таком механизме для доступных пользователю файлов.

## 14. Формулировка для технического описания проекта

> DuProve использует штатные файловые API Windows для обхода каталогов, получения метаданных и чтения содержимого. Текущий анализатор не реализует прямое чтение MFT или секторов тома. Сканирование выполняется в пределах разрешений процесса; недоступные объекты учитываются как ошибки, влияющие на полноту результата. Для анализа доступных пользователю файлов повышение прав администратора не требуется.

Эта формулировка основана на проверенных исходниках. Она не является аттестацией безопасности конкретного бинарного файла и не объясняет результат антивирусной проверки.
